## 二、目录职责

### `01-工程说明书/`　给评审与使用者

回答「系统是什么、怎么用、数据可信吗」。三份都是**结论性文档**，
不含代码细节，适合直接转给别人看。

| 文件 | 内容 | 读者 |
|---|---|---|
| `项目说明与进展证明清单.md` | 大白话版项目说明 + 每个阶段结论对应的可复现命令与材料清单 | 老师、评审、复盘 |
| `交付物说明.md` | 四份交付物各自的打开方式、内部结构、使用动线；含重建命令 | 要用交付物的人 |
| `演示前端与示例数据说明.md` | 怎么启动、打开后看到什么、8 件作品的 12 个 JSON 字段从哪来 | 要自己跑一遍的人 |

### `03-选题材料/`　给选题评审

| 文件 | 内容 |
|---|---|
| `选题报告.md` | 选题论证正文（Markdown 源）。同名 Word 版在 `output/01-交付物/` |

### `verify/`　证据，不是说明

这个目录的路径被 `scripts/build_docx.py` 以文字形式写进 Word 正文（「记录见 docs/verify/…」），

| 文件 | 是什么 | 谁产生 |

## 三、命名约定

本目录及 `output/` 下统一遵守三条：

1. **编号前缀表示阅读顺序**，不表示重要程度。
2. **目录名用中文**，因为要交给不看代码的人；**代码目录用英文**（`app/ sql/ tests/ scripts/`），因为要被工具链解析。
3. **不带日期的名字表示当前有效版本**；实测报告保留日期，便于对应环境与数据。

## 四、与 output/ 的分工

容易混，一句话分清：

| | `docs/` | `output/` |
|---|---|---|
| 本质 | 说明与证据（Markdown / 日志） | 可交付成品（docx / html / png / zip） |
| 能不能改 | 手写，随时改 | 脚本生成，**改了会被覆盖** |
| 给谁 | 要理解项目的人 | 要提交或展示的人 |

`output/` 的组织方式见 `output/产物清单.md`。
两个目录里的 docx 是**同源不同物**：`docs/03-选题材料/选题报告.md` 是源，`output/01-交付物/*.docx` 是排版后的成品。
