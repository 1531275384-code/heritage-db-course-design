# 第一部分：用大白话讲清这个项目

## 1. 一句话说清它是干什么的

**它解决的问题是**：村里绣娘绣了一个蝴蝶纹的绣片，她想申请版权。但这个蝴蝶纹其实几百年前就有，是"公家的东西"。如果直接给她发个版权证，那她就能拿着这个证去告别的绣娘侵权——这就不对了。

**这套系统做的事**：帮专家判断"这个作品到底是公家的（公有母题）、是改编的（改编衍生）、还是她自己原创的（原创作品）"，并且**把整个判断过程完整记录下来，事后谁都能查、谁都改不了**。

## 2. 用一个具体故事走一遍

假设绣娘杨秀英上传了一张绣片照片。系统里发生了这些事：

**第一步：她上传**
系统算出这张图的"数字指纹"（哈希值）。如果这个指纹数据库里已经有了，就直接告诉她"这张图已经登记过了，编号是 1"，不会重复建一条记录。这防的是：同一个人反复上传同一张图，最后系统里有一堆重复的资产，权属关系乱成一团。

**第二步：系统给图"算特征"**
把图片压缩成 512 个数字（叫"向量"）。你可以理解成：给这张图打 512 个分——线条往哪个方向走、颜色偏蓝还是偏红、纹理是密还是疏。**同一个纹样不同人拍的照片，这 512 个数字会很接近；不同纹样会差得远。**

**第三步：拿这 512 个数字去母题库里比**
系统里预存了 3 个公有母题的向量（蝴蝶纹、缠枝莲纹、回纹）。把新图跟这 3 个逐一算"像不像"（余弦相似度，0 到 1 之间，1 是完全一样）。

假设算出来：跟蝴蝶纹 0.9182，跟缠枝莲纹 0.65，跟回纹 0.71。

**第四步：系统给个"建议"——注意，只是建议**

规则很简单：
- 跟最像的那个母题像到 **0.92 以上** → 建议判"公有母题"（这就是传统纹样，你不能独占）
- 在 **0.80 到 0.92 之间**，而且有**两个以上**母题都落在这个区间 → 建议判"改编衍生"（你确实加了东西，但明显借鉴了传统，你有改编部分的版权，但不能禁止别人用原始纹样）
- **0.80 以下** → 建议判"原创作品"（跟现有母题没关系，倾向认为是你自己创作的）

上面那个 0.9182 落在 0.80~0.92 之间，系统就说："建议判**改编衍生**，因为跟『蝴蝶纹』相似度 0.9182，明显借鉴了但没到整体复制。"

同时系统还会算一个**置信度**（这次是 0.437）。这个数字不是装饰——它告诉专家"这个结论有多靠得住"。因为 0.9182 离 0.92 这条线非常近（只差 0.0018），所以置信度自动被压低。**系统在暗示：这个结论压在边界上，你得仔细看。**

**第五步：最关键的一点——AI 到这儿就停手了**

系统把"建议改判衍生"这句话写进审核表，但它**绝对不碰资产真正的权属字段**。

这一点是整个项目的核心，第七章会专门讲。此处你只要记住一个画面：截图中 AI 已经给出"改编衍生"的建议了，但资产状态那一栏还写着"草稿"、权级还写着"公有母题"——**AI 说了话，但一个字都没写上去。**

**第六步：专家来终审**

专家周文渊打开工作台，看到待审队列。他能看到：
- 这张图是谁传的
- AI 建议什么级别、多少置信度、最像哪个母题、相似度多少
- 完整的分级理由（AI 不是甩个数字，是写了一段人话解释）

专家看完选"原创作品"（他可以推翻 AI，这次他就推翻了），写一句意见，点终审。

**第七步：点下终审的那一瞬间，系统做了 6 件事，而且要么全成要么全不成**

1. 把这条资产记录**锁住**（防止另一个专家同时点终审）
2. 检查状态：必须是"待审"，已通过的不让再审
3. 把审核表里那条记录改成"已通过"，填上专家名字、结论、意见
4. 把资产表的权级改成"原创作品"、状态改成"已确权"
5. → 改资产表的这个动作，**数据库自己**触发了审计日志，记下"从公有母题改成原创作品，改的人是谁、什么时候"
6. 回头去读那条日志，确认它真的被写进去了

这 6 步在同一个事务里。中间任何一步失败，**前几步全部撤回**。更要紧的是第 5 步的日志也在同一个事务里——所以不会出现"日志说改了但数据其实没改"这种鬼事。

**第八步：事后查账**

任何人（监管部门）点开这件资产的"溯源"，看到一条时间线：

```
1. 资产登记            杨秀英        2026-10-26 14:16
2. DB 自动审计: -       db_trigger    2026-10-26 14:16   ← 上传时触发器记的
3. DB 自动审计: audit_status          2026-10-26 14:16
4. 专家终审通过        周文渊        2026-10-26 14:16   ← 专家判断
5. DB 自动审计: right_level,audit_status  db_trigger   ← 改权属时触发器记的
```

注意第 2、3、5 条，操作人写着 `db_trigger`——**这些不是程序代码写的，是数据库自己在数据变化时自动记的。** 这就是"事后谁都改不了"的技术底气：程序可以不老实，数据库不会。

## 3. 三个角色，各能干什么

| 角色 | 大白话 | 能干什么 | 不能干什么 |
|---|---|---|---|
| **传承人**（绣娘） | 交作业的人 | 上传作品、触发 AI 分析、看自己的作品、登记授权 | 不能终审、不能改权属、看不到别人的作品 |
| **专家**（评审员） | 判作业的人 | 看待审队列、写终审结论、改权级、驳回 | 不能改审计日志、不能删审核记录 |
| **监管方**（文化局） | 查账的人 | 看全部资产、看台账统计、管母题库 | 不能改权属结论 |

这三个角色不是前端菜单藏起来就算数的——**数据库层面就给了不同的权限**。传承人的账号就算绕过网页直接发请求去改权级，数据库也会拒绝。这是"数据库自己拒绝"，不是"网页不给你按钮"。

## 4. 各模块怎么咬合在一起的（依赖关系）

系统分五层，像流水线一样，每层只跟上下相邻的层打交道：

```
【第 1 层】网页（index.html + app.js）
              ↓ 发 HTTP 请求，带登录令牌
【第 2 层】门卫 + 调度（api.py + auth.py）
              ↓ 验令牌、查这个人的角色够不够、把请求转给下面
【第 3 层】业务逻辑（services.py）
              ↓ 只有这层会写 SQL，只在这层管事务边界
【第 4 层】AI 三件套（ai/ 目录）
              ↓ 只管算，不管存
【第 5 层】数据库（PostgreSQL + 8 张表 + 触发器 + 视图）
```

**依赖方向是单向的**，从第 1 层往下指，绝不反过来。这个规则的具体体现：

- 网页不知道数据库长什么样，它只知道"调用 `/api/ledger` 会拿到一组统计数据"
- 门卫不懂业务，它只做三件事：验令牌、查角色、转发
- **业务层是唯一写 SQL 的地方**——这条很关键，如果 SQL 散落在各处，事务边界就不可能管好
- AI 层不 import 任何数据库模块，所以它在物理上就写不了数据（第 7 章细说）
- 数据库不认识"专家"这个概念，它只知道"ich_expert 这个角色有权限改这几个列"

**几个具体的咬合点**，能看出依赖设计：

**① 分级器为什么碰不到数据库**

`app/ai/classifier.py` 的 import 清单里只有 `dataclasses` 和 `app.config`。没有 `app.db`，没有 `app.services`。

这不是写代码顺手写成这样的，是**故意的**。一个模块手里没有数据库连接对象，它在物理上就写不了数据。这比"记得别写"可靠得多——因为"记得"是会忘的，而"没有连接对象"是忘不掉的。

**② 演示模式怎么做到不改一行路由代码**

`app/demo.py` 里实现了一套跟 `services.py` **同名同参数同返回值**的函数。所以 `api.py` 里只需要这么一行：

```python
fn = demo.xxx if demo.is_enabled() else services.xxx
```

路由逻辑、鉴权、参数校验全部复用。这不是巧合，是设计时刻意对齐函数签名换来的。

**③ 视图是给谁用的**

三个视图分别被三个接口用：

| 视图 | 谁用 | 用它解决什么 |
|---|---|---|
| `v_asset_pending_audit` | 专家工作台的待审列表接口 | 要"待审资产 + 最新一条审核流水 + 从 JSONB 里掏出 top1 母题名"，这是多表关联 + LATERAL 子查询。写一次在数据库里，比在 Python 里拼稳妥 |
| `v_asset_trace_chain` | 溯源接口 | 要把"登记/审核/授权/DB审计"四类事件用 `UNION ALL` 拼成统一形状再按时间排。这种活儿应用层做容易出错 |
| `v_asset_ledger` | 台账接口 | 一资产一行，还要聚合授权数、金额、审计痕迹数。`LEFT JOIN LATERAL` + `FILTER` 子句是 SQL 的强项 |

**这三个视图的存在意义**：这些查询又长又容易写错，一旦写错，网页上看到的就是错数据。放在数据库里，就只有一份"正确版本"，改的时候也只改一处。

**④ AI 分析函数和终审函数，写的东西完全不一样**

| 函数 | 能写 | 绝对不能写 |
|---|---|---|
| `analyze_asset()`（AI 分析） | 审核表插一条待审记录、资产表的 `ai_suggest_level`（建议）字段 | **`asset.right_level`（真正的权属）** |
| `approve_asset()`（专家终审） | 审核表改成已通过、资产表的 `right_level` 和 `audit_status` | — |

这是整个系统唯一两个会写审核结论的函数，职责截然不同。有测试专门盯着这个区别（第 7 章）。

**⑤ 上传时算的哈希，和母题查重共用一个索引**

上传时用 SHA-256 哈希查"这张图是不是传过"，这个查询走了 `idx_asset_file_hash` 索引。同一个哈希概念，在"防止重复确权"和"防止重复上传"两件事上都用到了。

## 5. AI 为什么改不了权属——用大白话讲四道锁

需求里有一句话："**AI 只写建议，绝不直接改 `asset.right_level`**"。

如果只是写在文档里，三个月后必然有人为了赶需求加一句"AI 置信度高就自动确权吧"。所以项目上了四道锁，一道比一道硬：

### 第一道锁：数据库不给这个权限（最硬）

数据库里，传承人这个角色的授权清单是这么写的：

```sql
GRANT UPDATE (title, description, file_path, ..., ai_suggest_level, ...)
    ON asset TO ich_heritor;
```

**清单里没有 `right_level`。**

意思是：就算程序代码写错了一行 `UPDATE asset SET right_level='original'`，数据库也会把这个请求打回去，抛一个"权限不足"的错。程序再怎么写 Bug，也改不动这个字段。

只有专家角色有这一列：

```sql
GRANT UPDATE (audit_status, right_level, motif_id) ON asset TO ich_expert;
```

这不是"网页上不给按钮"，是**数据库自己拒绝**。

### 第二道锁：测试会盯着源码看

`tests/test_invariants.py` 干的事很朴素：**把源码当文本读，搜字符串。**

- 检查 `analyze_asset` 这个函数的函数体里，有没有出现写 `right_level` 的 SQL → 不能有
- 检查全工程除了 `approve_asset` 之外，还有没有别的地方出现 `SET right_level` → 不能有
- 检查 `classifier.py` 有没有 import `app.db` 或 `app.services` → 不能有

64 项这样的检查。哪天有人偷偷加一条"AI 自动确权"的捷径，测试立刻红。

### 第三道锁：分级器手里没有"枪"

分级器（负责说"建议判衍生"的那个模块）**根本没有数据库连接对象**。它只能接收一串相似度数字、返回一个"建议"数据包。没有连接对象，就写不了数据——这不是纪律问题，是能力问题。

### 第四道锁：改了也会被记下来，而且记了就改不掉

就算前三道全被绕过，只要 `right_level` 变了，数据库的触发器会立刻记一笔：从什么改成什么、谁改的、什么时候、用的什么数据库角色。

而且这个日志表**自己也装了防篡改触发器**：任何 UPDATE/DELETE 操作直接抛异常。同时数据库层面 `REVOKE UPDATE, DELETE` 收回了权限。

**两头都堵：程序改不了，就算改得动，日志也留下来了。**

## 6. 这套东西的"边界"在哪（必须说清楚）

诚实很重要。以下这些是**当前做不到或没验证过**的：

**① 没有在真实 PostgreSQL 上跑过 SQL 脚本**

开发环境的系统策略禁止执行 `initdb`，也装不了 C 编译器（所以编译不了 pgvector）。所以四个 SQL 脚本**从来没有在真实数据库上执行过一遍**。

这是这个项目最大的验证缺口。替代做法是：逐行读代码 + 写静态检查 + 写负向回归测试。也确实用这套方法抓出了 4 个真实缺陷（其中 1 个是"整条终审链路走不通"级别的）。

但必须承认：**静态检查不能完全代替真实执行。** 详见报告 §5.4 和 §7.2。

**② 演示模式下，五样东西是不生效的**

| 什么 | 演示模式下的状态 |
|---|---|
| 数据库列级权限 | 不生效（内存存储没有 RBAC） |
| 真实触发器 | 用手写代码模拟，逻辑等价但不是数据库触发器 |
| CHECK / UNIQUE / 外键约束 | 只在代码里做必要校验 |
| HNSW 向量索引 | 改为 numpy 全量计算（结果更准，但大表会慢） |
| 事务隔离 / MVCC | 单进程，`FOR UPDATE` 退化成一把互斥锁 |

网页顶部那条**红色横幅**就是写这个的。不是装饰，是提示"你现在看到的是模拟环境"。

**③ 没有 pgvector 时，检索退化成全表扫描**

这不是"打折扣跑通"，是"换一种等价实现"——结果甚至比 HNSW 更准（精确排序）。但有两条限制：
- 复杂度 O(n)，数据量大就慢
- **不能用它来证明"HNSW 索引生效了"**。这个证据只能在装了 pgvector 的机器上取得（要看 `EXPLAIN` 里有没有 `Index Scan using ..._hnsw`）

**④ 内置特征后端没有"语义理解"能力**

它不是 CLIP，它只是统计线条方向、颜色分布、纹理疏密。所以：
- 不能用文字搜图
- 对大幅旋转不鲁棒（回纹转 4 度，相似度掉到约 0.75）
- 对透视变形敏感

想要更强效果，装 torch 后切 CLIP 后端即可（同样是 512 维，不用改表结构）。

**⑤ 分级阈值是经验值，不是统计标定出来的**

0.92 / 0.80 这两个数，是从样例纹样的实测分布上估出来的。正式做法应该是在真实非遗图像数据集上画 ROC/PR 曲线找最佳切点。README §11.1 写了方法，但**没做**——因为没有数据集。

**⑥ 系统输出的是"技术建议"，不是法律判决**

全程措辞都是"建议"。AI 的结论必须经专家终审才能写进权属字段。文档里明确声明"不构成法律意见"。

## 一、源码 · 数据库（4 个文件，1077 行）

### `sql/00_compat_vector.sql` — 142 行

**用途**：pgvector 兼容层。没有 pgvector 扩展时，用 `NUMERIC[]` + 自定义 `<=>` 运算符替代向量类型和余弦距离。

**进度信息**：
- 证明考虑了"目标环境可能装不上 pgvector"这一现实问题，并给出了等价实现而非砍功能
- 全部定义包在 `IF NOT ich_vector_is_native() ... END IF` 里——有原生扩展时一行都不执行，不与原生运算符冲突。这体现了"兼容层不能污染主路径"的设计意识
- 是"能不能真实运行"这个问题的直接答案

**关键代码**：
```sql
CREATE OR REPLACE FUNCTION ich_cosine_distance(a NUMERIC[], b NUMERIC[])
RETURNS DOUBLE PRECISION ...
    RETURN 1.0 - (dot / (sqrt(na) * sqrt(nb)));
CREATE OPERATOR <=> (LEFTARG = NUMERIC[], RIGHTARG = NUMERIC[], FUNCTION = ich_cosine_distance);
```

### `sql/01_init.sql` — 313 行

**用途**：建扩展、建 3 个枚举类型、建 8 张业务表、加全部约束与字段注释。

**进度信息**：
- 8 张表齐备：`app_user` / `public_motif` / `asset` / `feature_vector` / `audit_record` / `license_record` / `asset_genealogy` / `system_audit_log`
- **24 条 CHECK 约束、12 个外键**——证明约束设计不是敷衍了事

**用途**：分级建议器。把相似度数字翻译成"公有母题/改编衍生/原创作品"的建议。

**进度信息**：

## 九、必须同时说明的一件事

这批文件能证明的东西很扎实，但有两处缺口必须在提交时主动说明。

**更新（2026-11-02）：原先最大的那条缺口已经补上了。**

> ~~四个 SQL 脚本从未在真实 PostgreSQL 上执行过。~~
>
> **现已执行。** 用便携版 PostgreSQL 16.2 二进制起本地实例（端口 55432），
> `python -m scripts.pg_run --reset` 从空库重建（119 条语句 / 约 1.6 秒，连续两次重建对象完全一致），
> `python -m tests.check_pg` 真实库验收 **35 项通过 / 0 失败 / 1 缺口**。
> 证据：`docs/verify/pg_run.log`。

已实测：列级 GRANT、8 个触发器（已终审不可改、日志禁改禁删、自己授权给自己被拒、
未终审不得授权、已驳回不得授权）、CHECK 与枚举约束、事务回滚、
`FOR UPDATE` 行锁互斥（55P03）、降级向量层 cosine 语义，
以及专家终审的完整链路（`ich_expert` UPDATE → 触发器代写日志 → `version_no` 自增 →
日志 actor 记为 `ich_expert` 而非建库账号）。

仍然存在的缺口只剩一项：

| 缺口 | 原因 | 影响 |
|---|---|---|
| HNSW 索引未实测 | 便携包不含 pgvector，走 `NUMERIC[]` 精确扫描 | 不能声称检索性能，只能声称功能等价 |

原先的第二项「未终审不得授权只在应用层」，已在 2026-11-08 补成数据库约束
`trg_license_require_approved`（BEFORE INSERT，按 `asset.audit_status = 'approved'` 判定），
绕过 API 直接写库同样被拒。数据库里现有的 5 笔授权全部落在已终审作品上，加约束没有挡住合法数据。

真实库一共暴露 8 个缺陷，全部只在真跑时出现：3 个是 SQL 语法/运算符问题
（美元引用嵌套、数组除标量、`ROUND(double,int)` 重载），
另外 5 个是**只有跑起来才会撞到的权限与语义问题**——
其中最严重的三个分别是「任何 `UPDATE asset` 都崩」（含专家终审）、
「没有任何角色能写 `license_record`」（登记授权功能封死）、
「审计触发器以调用者身份执行」（终审时写日志 permission denied）。
这三条都不是语法错误，静态检查永远查不出来，只能靠真跑。

但这些都不能完全等同于"在真实数据库上跑通一次"。

**提交时建议同时给出**：README §1.0 的三条命令。在任意一台有 Docker 的机器上，那三条命令就能补上这个缺口。所有脚本、诊断工具、文档都已就位，缺的只是一台能装 PostgreSQL 的机器。
