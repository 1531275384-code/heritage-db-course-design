## 二、Word 文档

### 2.1 用什么打开

用 Microsoft Word、WPS、Pages 均可。**推荐用 Word 或 WPS**（目录域需要它们刷新）。

### 2.2 打开后请先做一步

文档第 2 页是目录页，因为用的是 **Word 自动目录域**（不是手写的固定文字），
首次打开时显示的是占位提示。请按下面任一种方式生成带页码的目录：

- 按 `Ctrl + A` 全选，再按 `F9`
- 或右键点击目录区域 → 选择「更新域」→「更新整个目录」

> 为什么用域而不直接写好？因为手写目录一旦改了正文就会全错，且没人会记得去改它。
> 用域则一条命令就能重新生成。实测中我也确认过：目录层级正确识别到二级标题。

### 2.3 文档结构

```
封面
目录（自动域）
一、文档说明 ........................... 回答四个问题、阅读顺序建议

    图 2-1 AI 分析面板
    图 2-2 母题库页面
三、系统设计 ........................... 8 张表职责、3 个视图、触发器、权限模型
    图 3-1 作品列表（三个字段的直观对比）
    图 3-2 监管台账

    图 4-1 专家工作台
```

**规模**：7 章、28 节、31 张表格、5 张界面截图，约 40 页。

### 2.4 排版上的几个处理

- **页眉页脚**：页眉标注文档名，页脚居中显示「第 X 页」，页码同样用域实现。
- **表格**：朱砂色表头、隔行浅底、跨页自动重复表头（长表格翻页后仍能看到列名）。
- **提示框**：正文中有三类彩底提示框——靛蓝（关键设计说明）、朱砂（风险与警告）、
  灰色（容易混淆的点），用于把重要信息从正文里拎出来。
- **代码块**：SQL 片段用等宽字体加浅底框，与正文区分。
- **图片**：均带「图 X-X」题注，宽度统一，不跨页断裂。

> 关于排版的一个细节：表格列宽我最初只设了单元格宽度，结果 Word 仍按三等分渲染，
> 导致「层次」这种短列文字被挤成竖排。原因是固定布局下 Word 以 `tblGrid` 为准，
> 必须同时改网格列宽。现已修正并加脚本校验（31 张表的网格与单元格宽度全部一致）。

### 3.3 纯界面版：四个可以现场操作的功能

**① 切换身份（顶栏右上）**

点「传承人 / 评审专家 / 监管管理员」，页签与数据范围立刻变化：

| 身份 | 可见页签 | 说明 |
|---|---|---|
| 传承人 | 我的作品 / 母题库 / 作品上传 | 只能看到自己的作品 |
| 评审专家 | 母题库 / 作品上传 / 专家工作台 / 监管台账 | 能看全部、能终审 |
| 监管管理员 | 母题库 / 作品上传 / 专家工作台 / 监管台账 | 全量只读 |

> 现场可以这样讲：传承人看不到「专家工作台」和「监管台账」。
> 这不是前端把按钮藏了——真实系统里后端会返回 403，
> 数据库层面更没有权属字段的写权限。

**② 模拟上传与 AI 分析（作品上传页签）**

选一份内置样例 → 点「上传并触发 AI 分析」→ 右侧出现：
- AI 建议档位与置信度
- 三条母题的相似度条形图（0.9182 / 0.4255 / 0.3743）
- 特征模型名、向量维度、命中规则
- **权属级别显示为「未定」，并注明「AI 未写入，等待专家终审」**

这几个数字都来自 `docs/verify/run_result.json` 里记录的真实算法输出，不是编的。

**③ 专家终审（专家工作台页签）**

点任一待审作品的「终审」按钮 → 三档可选（公有母题 / 改编衍生 / 原创）→
选一个**与 AI 建议不同**的档位，立刻出现红字提示：「与 AI 建议不同，将记为『推翻 AI』」→
填意见 → 提交。

提交后：该作品状态变为已确权、待审队列减少一件、统计数字随之更新、提示「已终审（推翻 AI）」。

弹窗底部还写明了真实系统里这一操作会做的六步事务，可以顺势讲「为什么权属只能由专家写」。

**④ 重置（顶栏）**

终审操作会真实改变演示数据。点「重置」恢复初始状态，刷新页面也会重置。

### 3.4 其他可看的内容

- **母题库**：三张母题卡片（参考图 + 民族 / 类别 / 年代 + 关键词标签），可按民族筛选；
  下方是母题与作品的关联表，直接体现「母题血缘」。
- **作品详情**：点任意作品行，弹出详情——创作说明、溯源链路时间轴（含专家意见原文、
  是否推翻 AI）、授权记录。
- **监管台账**：授权费合计 ¥131,600、5 笔授权明细、每件作品的母题编码与 Top-1 相似度。

### 3.5 讲解动线建议

如果只有 3 分钟：

1. 停在默认的传承人「我的作品」——指出三列的分工：AI 建议 / 专家结论 / 状态
2. 点开一件待审作品——「AI 给了建议，但权属是空的，这就是核心命题」
3. 切到专家 → 工作台 → 终审 → 故意选不同档位——「推翻 AI 会被记录下来」
4. 切到台账——「授权费合计、每件作品的母题来源，全在台账里」
5. 切回传承人，指出没有「监管台账」页签——「看不到，不是藏起来的」
6. 收尾一句——「传承人不仅看不到监管台账，直接连库改权属状态也会被触发器拒绝」。
   这一句是真库模式的卖点：`audit_status` 必须给传承人写权限（草稿、提交待审都要用），
   所以列级授权堵不住"自己把状态推到已确权"，堵它的是 `trg_asset_status_guard`；
   以 `ich_heritor` 身份执行 `UPDATE asset SET audit_status='approved'`，
   返回的是数据库的 42501，不是应用层的 403

有 5 分钟就再加母题库和 AI 分析两段。

## 五、怎么重新生成（改了内容之后）

四份产物都是脚本生成的，不是手写的，所以改了数据或代码后可以一键重建：

```bash
# 重新生成 Word 文档
.venv/Scripts/python.exe scripts/build_docx.py

# 重新生成纯界面版（默认不带左侧说明栏）
.venv/Scripts/python.exe scripts/build_demo_page.py

# 需要连说明栏一起出，加参数
.venv/Scripts/python.exe scripts/build_demo_page.py --with-doc

# 重新生成互动版
.venv/Scripts/python.exe scripts/build_demo_v2.py

# 验收两个演示页
.venv/Scripts/python.exe -m tests.check_demo_page   # 52 项，纯界面版
.venv/Scripts/python.exe -m tests.check_demo_v2     # 58 项，互动版
```

`build_docx.py` 里的所有数字（账号数、作品数、授权费合计、日期）都从
`data/seed_demo.json` 实时读取，不硬编码。所以改了种子数据，重新跑一次脚本，
文档里的数字会自动跟上，不会出现「文档说 8 件、系统里 9 件」这种不一致。

互动版的样式与脚本放在 `scripts/v2_assets/`（`style.css` / `login.html` / `app.html` /
`app.js` / `pages1.js` / `pages2.js`），`build_demo_v2.py` 只负责读数据、拼装、内嵌。
拆开的原因是 JS 里大量模板字符串，塞进 Python 三引号会陷入转义地狱。

## 七、需要说明的两点

**第一，两个演示页都不是真实系统。** 它们是静态页面，数据是种子数据的内嵌副本，
终审、授权等操作只改浏览器内存，不写任何数据库；登录也只是前端校验，不是真的鉴权。
要验证真实读写，需要用 `python bootstrap.py --demo` 或 `--strict` 启动后端。

**第二，数据库部分已经在真实 PostgreSQL 上跑通了，只剩一处无法解决的缺口。**

早先的情况是开发环境建不了库（`initdb` 被安全策略拦、pgvector 编不了），SQL 只有静态校验。
这个问题已经解决：用便携版 PostgreSQL 16.2 二进制起了一个本地实例（端口 55432），
`python -m scripts.pg_run --reset` 可从空库一键重建（119 条语句，约 1.6 秒），
`python -m tests.check_pg` 做真实库验收，**35 项通过 / 0 项失败 / 1 项缺口**。
完整执行日志见 `docs/verify/pg_run.log`。

已经验证到的：列级授权、8 个触发器（含「已终审不可改」「日志禁改禁删」「自己授权给自己被拒」
「未终审不得授权」「已驳回不得授权」）、CHECK/枚举约束、事务回滚、
`FOR UPDATE` 行锁互斥（第二个会话拿到 55P03）、降级向量层的 cosine 语义，
以及**专家终审这条主链路**：以 `ich_expert` 身份执行 UPDATE、触发器代写审计日志、
`version_no` 自动 +1、日志里记下操作者是 `ich_expert` 而非建库账号。

仍然没验证的只有一项，如实列出：

| 缺口 | 原因 | 影响 |
|---|---|---|
| HNSW 索引未实测 | 便携包不含 pgvector，只能用 `NUMERIC[]` + 精确扫描 | 「检索快」这个结论不成立，只能说功能等价 |

原先列在这里的第二项「未终审不得授权数据库层未拦截」，已经补上：
`trg_license_require_approved` 在 `license_record` 的 BEFORE INSERT 上按 `asset.audit_status`
判定，绕过 API 直接写库同样被拒（`23514`）。数据库里现有的 5 笔授权全部落在已终审作品上，
所以加约束没有挡住任何合法数据。

真实库一共暴露过 8 个缺陷，全部只在真跑时出现，静态检查与代码审查一个都没抓到：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 兼容层用 `$$` 作标签嵌在 `DO $$` 里 | 美元引用不能嵌套，整个脚本解析失败 |
| 2 | 归一化触发器写「数组 ÷ 标量」 | PostgreSQL 没有这个运算符，两种模式都报错 |
| 3 | 兼容层写 `ROUND(double precision, int)` | 没有此重载，必须先转 NUMERIC |
| 4 | 触发器里 `TEXT[] \|\| '字面量'` 拼变更列名 | **任何 UPDATE asset 都崩**，包括专家终审 |
| 5 | `healthy()` 把「无 pgvector」判为不可用 | 完全可用的降级库被误判，灌数据脚本拒绝执行 |
| 6 | `license_record` 三个角色都只有 SELECT | **登记授权在真库上必然 42501**，核心功能封死 |
| 7 | 灌数据脚本用 `ich_admin` 写资产 | 该角色无 asset 写权限；清理逻辑还假设外键是 CASCADE（实际 RESTRICT） |
| 8 | 审计触发器为 SECURITY INVOKER | 专家终审时触发器写日志 permission denied，整个事务回滚 |

第 4、6、8 条是同一个主题：**「权限收紧」与「触发器代写」在设计上要配套**。
只收紧权限不给代理，功能就死了；只给代理不收紧，审计就可伪造。现在的做法是
审计触发器 `SECURITY DEFINER` + `search_path` 固定，业务角色对 `system_audit_log`
依然只有 SELECT —— 既跑得通，也伪造不了。
