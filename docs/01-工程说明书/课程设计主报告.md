# 非遗数字资产分级确权与溯源系统
## 《数据库原理》课程设计主报告

> **权威版本：2026-11-27**  
> 本报告为本课程设计的唯一权威技术报告，数据以当前仓库 SQL、PostgreSQL 16.15 + pgvector 0.8.6 实测记录及 `python tests/run_all.py --all` 的最新汇总为准。系统围绕非遗纹样数字资产建立“登记—分析—审核—授权—溯源”闭环，重点展示关系数据库设计、事务与并发、权限控制、索引优化和备份恢复。

## 摘要

本课程设计针对非遗纹样进入数字展示和文创衍生环节后，来源、权属结论与授权记录容易分散的问题，构建基于 PostgreSQL 的非遗数字资产管理系统。系统将公有母题、作品资产、特征向量、审核流水、授权记录、衍生谱系和系统审计纳入统一数据模型；由图像特征引擎提供母题相似性参考，由专家完成权属等级终审，数据库通过约束、列级授权、触发器、事务和视图维护数据一致性与操作可追溯性。

系统包含 8 张业务表、4 个视图、10 个触发器和 3 个业务角色。`feature_vector` 与 `asset` 采用一对一垂直拆分；`asset_genealogy` 以有向无环图表达衍生关系；`license_record.prev_license_id` 串接授权变更。真实 PostgreSQL + pgvector 验收、并发验证、规则对拍、浏览器验收及备份恢复均有可复现记录。当前全量自动化基线为 **15 套、641 项断言、0 失败**。

**关键词：** PostgreSQL；关系数据库；非遗数字资产；完整性约束；事务并发；pgvector；审计溯源

## 1. 选题背景与业务需求

非遗纹样常以图像、扫描件或设计稿的形式进入数字资源库和文创开发流程。业务管理需要同时回答：资产来自何处、关联哪些传统母题、权属等级由谁审核、授权给谁以及后续作品如何衍生。若这些信息仅保存在图片文件名、表格或应用日志中，跨环节核对和追责会变得困难。

本系统将问题转化为数据库可管理的业务对象和规则：

1. **资产登记与查重：** 保存原始文件摘要、所有者、母题关联及入库时间；SHA-256 摘要用于文件一致性核验和重复检测。
2. **辅助分析与人工终审：** 特征模型检索相似母题并生成可追溯的分析快照；机器输出仅作为建议，`right_level` 由授权专家终审写入。
3. **授权登记与链式追踪：** 保存授权类型、对象、期限、费用、合同摘要及前序授权记录。
4. **衍生作品血缘：** 以有向边记录“母资产—衍生资产”关系，递归查询作品的上游来源。
5. **审计与监管：** 通过数据库触发器形成资产关键字段变更日志，并按角色提供受控查询入口。

系统的数据库目标是保证记录完整、一致、可追踪和可恢复。特征相似度用于检索和审核辅助，不替代专家判断或法律认定。

## 2. 总体架构与业务流程

系统由 Web/API 服务、特征分析层和 PostgreSQL 数据层组成。业务操作在应用服务中编排；数据库保存权威状态、执行完整性规则并记录关键变化。数据库采用 PostgreSQL 16.15，原生向量模式使用 pgvector 0.8.6；两类向量检索索引均使用 HNSW。

**业务流程：**

```text
上传并登记资产
  → 保存 SHA-256、所有者和元数据
  → 特征提取与公有母题近邻检索
  → 写入审核申请及分析快照
  → 专家在事务内完成终审并更新资产等级
  → 依据已审核状态登记授权及合同摘要
  → 追加衍生血缘边、查询授权链与祖先链
  → 触发器生成审计记录，视图提供角色化查询
```

终审过程中，资产状态、审核流水与系统审计处于同一数据库事务中；任一环节失败则整体回滚。

## 3. 概念结构与关系模式

### 3.1 八张核心业务表

| 关系 | 主键与主要联系 | 主要职责 |
|---|---|---|
| `app_user` | `user_id`；`username` 唯一 | 用户身份、业务角色、组织及启用状态 |
| `public_motif` | `motif_id`；`motif_code` 唯一 | 公有领域传统母题、参考图及 512 维基准向量 |
| `asset` | `asset_id`；`owner_id` 外键至用户；`motif_id` 外键至母题 | 数字作品元数据、文件摘要、机器建议、人工确认等级、状态和版本号 |
| `feature_vector` | `fv_id`；`asset_id` 外键至资产并保持资产级唯一 | 资产特征向量、模型名称与版本，支持重新提取和近邻检索 |
| `audit_record` | `audit_id`；关联资产与审核专家 | 多轮审核状态、机器建议快照、相似母题快照、专家结论与意见 |
| `license_record` | `license_id`；关联资产、授权方、被授权方；`prev_license_id` 自引用 | 授权类型、期限、范围、费用、合同摘要、状态和前序授权关系 |
| `asset_genealogy` | `genealogy_id`；父、子资产外键；父子组合唯一 | 记录作品衍生边，构成可查询的有向无环图 |
| `system_audit_log` | `log_id`；记录表名、记录主键和操作主体 | 记录关键业务表变化前后快照、变更字段与操作时间 |

主要联系可概括为：一个用户可拥有多项资产；一项资产可关联一个公有母题、多个审核流水和多个授权记录；资产特征按资产一对一保存；谱系边连接两项资产；系统审计日志以“表名 + 记录 ID”定位被审计对象。

### 3.2 规范化与垂直拆分

用户、母题、资产、审核、授权与谱系分别表达独立实体，外键维护实体间联系；关系模式按第三范式组织：每个非键属性依赖于键、依赖于整个键且不传递依赖于其他非键属性；每张表以主键标识记录，非键属性描述所属实体，避免把多个审核或授权事件重复嵌入资产行。审核和授权分别使用独立流水表，使多次审核、授权续期和撤销能以多行记录表达。

`feature_vector` 与 `asset` 通过 `asset_id` 建立一对一关系。向量元数据和嵌入值只服务于相似性计算，与资产列表、审核状态等日常读写负载不同，因此独立存放能缩窄主表行宽，减少不需要向量的查询触碰 TOAST 数据。该拆分是物理布局优化；逻辑关系仍由唯一性、外键与应用事务保证一对一。模型版本保留在特征表中，允许更新特征时识别数据来源。

审核记录中的机器建议和相似度 JSON 是当次审核的**历史快照**，用于复核“审核当时所见”的信息；它们属于事件事实，不是用于替代资产当前状态的重复字段。`asset.right_level` 保存终审后的当前等级，`audit_record.expert_level` 保存具体审核结论。

### 3.3 DAG 血缘与授权链

`asset_genealogy(parent_asset_id, child_asset_id)` 中一条边表示“子作品衍生自父作品”。外键保证节点存在，`CHECK` 阻止自环，唯一约束阻止重复边，递归触发器阻止多跳闭环。该关系允许菱形 DAG：同一祖先可以经不同路径到达某个衍生作品。

`license_record.prev_license_id` 指向前一条授权记录。续期、变更或撤销通过追加新记录并建立前序关系保存授权轨迹；合同文件摘要可用于核验合同文件是否与登记时一致。DAG 表达作品之间的衍生关系，授权自引用链表达同一资产的授权流转，两者分别承担不同的溯源语义。

## 4. 完整性约束与安全权限

### 4.1 数据完整性

数据库通过以下规则保证数据质量：

- **实体与参照完整性：** 主键、外键、唯一约束约束用户、母题、资产、审核与授权间的引用；删除策略保护仍被资产、审核或授权引用的记录。
- **域完整性：** 枚举类型限定权属等级、审核状态和角色；`CHECK` 校验文件 SHA-256 格式、文件大小、置信度范围、版本非负、向量 512 维、授权期限及费用等。
- **业务规则：** 部分唯一索引保证同一资产最多一条有效独占授权；授权触发器要求资产先完成审核；审核状态迁移触发器约束角色可执行的状态变化。
- **审计完整性：** 资产关键字段变化触发快照日志；审核流水不可删除，已终审记录不可再修改；系统审计日志只追加。

### 4.2 三角色权限矩阵

| 角色 | 业务责任 | 主要数据库权限边界 |
|---|---|---|
| `ich_heritor` 传承人 | 登记本人作品、提交审核申请、查看授权及溯源 | 可读公共母题和授权视图；资产仅授予指定非权属列写权限，不可直接改 `right_level`；不可修改审计日志 |
| `ich_expert` 专家 | 审阅申请并作出终审结论 | 可写审核流水；仅可更新资产的 `audit_status`、`right_level`、`motif_id` 指定列；终审标记须在事务范围内设置 |
| `ich_admin` 监管管理员 | 维护公有母题并监督全局记录 | 可查询全局业务数据和审计记录，可维护母题；不直接写资产权属等级，避免审核与监管职责混同 |

权限在 PostgreSQL 层以角色和**列级 GRANT**落实。应用事务通过 `SET LOCAL ROLE` 在事务局部切换数据库角色，事务结束后自动恢复连接原有身份；与普通应用层角色判断相配合，减少连接池复用造成的权限残留。

### 4.3 事务闸门与十个触发器

专家终审通过 `ich.finalize_gate` 事务级标记授权终态写入。服务在同一事务内设置标记、更新审核流水和资产等级；`trg_asset_status_guard` 验证角色及标记，阻止绕过终审流程的直接改写。事务回滚时标记、业务更新和审计日志一同回滚。

当前 SQL 定义 10 个触发器：

| 触发器 | 作用 |
|---|---|
| `trg_asset_right_change` | 记录资产权属、状态、母题或所有者变化的前后快照 |
| `trg_asset_touch` | 更新资产修改时间和乐观锁版本号 |
| `trg_asset_status_guard` | 验证资产状态迁移的角色与终审事务标记 |
| `trg_audit_record_no_delete` | 禁止删除审核流水 |
| `trg_audit_record_guard` | 保护已终审审核记录，并允许受控状态流转 |
| `trg_syslog_immutable` | 禁止修改或删除系统审计日志 |
| `trg_license_no_delete` | 禁止删除授权历史记录 |
| `trg_license_require_approved` | 仅允许对审核通过的资产登记授权 |
| `trg_genealogy_no_cycle` | 在插入或更新谱系边时递归检测成环并串行化并发建边 |
| `trg_motif_vector_norm` | 将母题基准向量归一化，保持 cosine 计算语义一致 |

## 5. 索引设计与查询优化

### 5.1 索引结构

- **B-Tree：** 支撑文件摘要精确查重、资产所有者与时间排序、权属等级筛选、审核与授权按资产查询、审计按目标或时间查询、谱系子节点查找等常见访问路径。
- **部分索引：** `idx_asset_pending` 针对待审资产建立过滤索引；`idx_asset_motif` 排除空母题；`uq_lic_exclusive_active` 只对有效独占授权施加唯一性约束，避免历史记录妨碍当前有效性判断。
- **GIN：** `idx_audit_record_sim_gin` 支持审核相似度 JSONB 快照检索。
- **pgvector HNSW：** `idx_public_motif_hnsw` 和 `idx_feature_vector_hnsw` 基于 cosine 距离服务母题和资产向量近邻查询。

SQL 脚本定义 14 个显式普通与向量索引；数据库系统目录实测与备份恢复逐项核对共 26 个索引对象，包含主键索引、唯一约束索引及部分唯一索引。

### 5.2 性能与物理存储实测

性能测量在 PostgreSQL 16.15 + pgvector 0.8.6 上执行，详细查询计划见 [`验收记录-20261126.md`](../verify/验收记录-20261126.md) 和 [`bench_20261126-193234.md`](../verify/bench_20261126-193234.md)。

| 场景 | 实测结果 | 解释 |
|---|---:|---|
| 5,000 条合成向量近邻检索 | HNSW 0.763 ms；禁用索引扫描 22.31 ms | 约 29 倍差异；默认计划实际使用 HNSW |
| 20,000 行资产列表，只取展示列 | 5 个顶层命中页，0.083 ms | 不读取向量时保持主表访问轻量 |
| 同样查询带上 512 维 embedding | 182 个顶层命中页，79 个读盘页，5.808 ms | 页数为展示列查询的 36.4 倍，体现垂直拆分避免读放大的效果 |
| 20,000 条向量的 HNSW top-5 | 1,353 页，3.05 ms | 近邻检索走向量索引 |
| 同一向量检索顺序扫描基线 | 117,450 页，209.74 ms | 本次样本中 HNSW 页数约少 86.8 倍、耗时约快 68.7 倍 |

## 6. 视图、递归查询与并发控制

### 6.1 四个视图

| 视图 | 作用 |
|---|---|
| `v_asset_pending_audit` | 为专家工作台组织待审核资产及最新审核信息 |
| `v_asset_trace_chain` | 将资产、审核、授权和审计事件统一成时间线 |
| `v_asset_ledger` | 汇总资产、授权数量、有效授权与费用等监管台账字段 |
| `v_asset_lineage` | 通过 `WITH RECURSIVE` 沿父节点方向展开任意深度祖先链，返回深度、路径和直接父节点标记 |

`v_asset_lineage` 的递归项沿 `asset_genealogy` 逐层查找祖先，并携带路径数组；路径检查防止异常循环无限递归，深度上限提供额外保护。多条合法路径可以让同一祖先在结果中出现多次，以保留 DAG 的多路径语义。

### 6.2 并发控制

- **悲观锁：** 专家终审通过 `SELECT ... FOR UPDATE` 锁定资产行。同一作品的并发审核会串行化；锁冲突由数据库等待，后续状态检查阻止重复终审。
- **乐观锁：** `asset.version_no` 随更新递增，客户端可用版本号检测并发修改，避免静默覆盖。
- **事务级咨询锁：** 谱系环检测在递归判断前取得 `pg_advisory_xact_lock`。不同资产行上的反向边不会被普通行锁自动互斥，该锁使并发建边逐个检查，从而阻止写偏斜生成环。
- **唯一性并发保护：** 有效独占授权由部分唯一索引约束；两个并发登记中最多一个能保留有效状态。

`concurrency_20261126.log` 记录了 30 项真实多会话验收：并发双专家终审恰有一个成功、外部持锁可观测到终审等待、并发独占授权恰有一条有效记录、反向谱系边并发插入仅一条落库；递归祖先链在直链与菱形 DAG 场景下均按预期返回。**30 项全部通过。**

## 8. 结论

本课程设计将非遗纹样登记、机器辅助检索、专家终审、授权登记和作品衍生血缘纳入同一关系数据库方案。其核心数据库设计包括规范化业务实体、特征数据垂直拆分、带历史关系的授权与审核流水、递归 DAG 查询、列级权限、事务闸门、10 个触发器、4 个业务视图以及面向关系查询和向量检索的组合索引策略。

系统已在真实 PostgreSQL + pgvector 环境完成结构、权限、事务、并发、近邻检索和备份恢复验证；全量自动化测试达到 15 套、641 项断言全部通过。课程答辩可按“登记一项资产—查看母题匹配—专家终审—登记授权—展示血缘与审计—查看数据库验收证据”的顺序演示。
