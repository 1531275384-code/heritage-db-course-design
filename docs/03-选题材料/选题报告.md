## 一、选题背景

### 1.1 现实问题：非遗数字化的"确权真空"

非物质文化遗产的数字化正在快速推进——纹样、绣片、器型被拍摄、扫描、矢量化后进入机构数据库与文创供应链。但数字化本身没有解决权属问题，反而制造了一个新的真空地带：

| 问题 | 具体表现 |
|---|---|
| **公有母题被独占** | 蝴蝶纹、缠枝莲纹、回纹这类流传数百年的传统纹样属公有领域，但某人把纹样稍作修饰后作为"原创作品"登记版权，进而向其他从业者主张权利，形成"传统资源的私人圈占" |
| **改编幅度无从量化** | "借鉴"与"抄袭"之间没有可度量的界线。目前完全依赖人工比对与专家经验判断，效率低、标准不一、难以复核 |
| **权属结论不可追溯** | 一个"原创"结论是怎么产生的、谁定的、依据什么，往往只存在于纸质档案或某个人的记忆里。一旦发生纠纷，举证困难 |
| **授权流转缺少存证** | 非遗传承人授权企业使用纹样，协议签完就散落各处，后续维权无法证明"这个纹样在何时被授权给谁以什么价格" |

这些问题的共同根源是：**权属判断是主观的、过程是断裂的、证据是不可验证的。**

### 1.2 技术切入点：图像相似度可以成为分级依据

非遗纹样的数字资产绝大多数是二维图像。这类图像具有一个对技术非常友好的特点：**母题的结构特征高度稳定**。

- 蝴蝶纹的对称双翼结构、缠枝莲纹的连续曲线缠绕关系、回纹的直角折线周期——这些不是创作者可以随意改变的东西，一旦改变就不成其为该纹样
- 因此"与既知公有母题的特征距离"可以作为"借鉴程度"的客观代理指标

这意味着一件事：**把权属分级问题转化为向量空间中的距离判定问题**。现代 CV 技术（CLIP、ResNet）可以把图像映射到 512 维语义空间，用余弦相似度度量"像不像"；PostgreSQL 的 pgvector 扩展提供了 HNSW 近似最近邻索引，能在毫秒级完成百万级向量的检索。

但这里有一个必须守住的边界——**相似度只能作为建议，不能作为判决**。这是本项目的核心设计立场，后文第四章会详细展开四层防护机制。

### 1.3 选题定位

本项目不追求"用 AI 自动定权属"。恰恰相反，它要回答的是另一个问题：

> **当 AI 已经能给出相当可靠的权属判断时，如何从工程上保证它不越界？**

这个问题比"怎么做相似度检索"更贴近数据库课程的核心——它涉及列级权限、事务原子性、触发器审计、视图抽象、并发控制。因此本选题是一个**以数据库原理为主干、AI 作为业务驱动**的综合设计题，而非一个 AI 调参题。

## 二、项目目标

### 2.1 总体目标

构建一个可运行的 Web 系统，实现非遗数字资产从**上传 → AI 特征提取与相似检索 → 分级建议 → 专家终审确权 → 授权流转 → 溯源查询 → 监管统计**的完整闭环，并在数据库层面强制保证"AI 只建议、专家终审、过程留痕、结论可溯"。

### 2.3 明确不做的事（范围边界）

清晰界定不做什么，比罗列做什么更能说明项目成熟度：

- **不做版权法律判定**。系统输出的是"技术层面的相似度与分级建议"，不构成法律意见
- **不做多模态跨模态检索**（文字搜图）。内置特征后端无语义理解能力，CLIP 后端具备但不在默认依赖内
- **不做生产级部署**（对象存储、限流、密钥管理）。这些在范围外，但在文档中逐条列出改造点
- **不构建大规模非遗图像数据集**。母题库仅 3 条种子数据，用于验证链路而非验证准确率

## 三、研究或开发内容

### 3.1 数据库设计（主体工作量）

#### 3.1.1 八张表与结构决策

| 表 | 职责 | 关键设计决策 |
|---|---|---|
| `app_user` | 用户与角色 | 口令用 pgcrypto 的 `crypt()` + `gen_salt('bf')` 存储，不用明文也不用应用层简单 hash |
| `public_motif` | 公有母题库 | 含 `base_vector VECTOR(512)`；**它是私有资产的比对基准，本身不受确权流程约束** |
| `asset` | 资产主表 | 同时持有 `right_level`（当前权属）与 `ai_suggest_level`（AI 建议）。**两列分离是设计的核心** |
| `feature_vector` | 特征向量 | 与 `asset` 1:1 垂直拆分。理由见 3.1.2 |
| `audit_record` | 审核流水 | 一次 AI 分析产一条，`state` 走 `pending → approved/rejected`；`similarity_json` 用 JSONB 存 top-K 快照 |
| `license_record` | 授权流转 | 有 `UNIQUE` 部分索引保证"同一资产同一被授权方只能有一条独占授权" |
| `asset_genealogy` | 母题血缘谱系 | 自引用外键（`parent_asset_id` / `child_asset_id`），支持表达"B 改编自 A" |
| `system_audit_log` | 数据库层审计日志 | 存 `old_snapshot` / `new_snapshot` / `changed_fields`，由触发器写入，应用层不可改 |

枚举类型三个：`right_level_enum(public, derived, original)`、`audit_status_enum(draft, pending, approved, rejected)`、`user_role_enum(heritor, expert, admin)`。用枚举而非字符串，是为了让非法值在**类型层面**就无法插入。

约束统计：**24 条 CHECK、12 个外键、多个 UNIQUE（含部分唯一索引）**。典型 CHECK 例如"`ai_confidence` 必须在 [0,1]"、"`approved` 状态必须有 `decided_at`"、"`parent_asset_id != child_asset_id`（防自环）"。

#### 3.1.2 为什么 `feature_vector` 要垂直拆分

这是一个值得单独讨论的设计决策。把 512 维向量直接放 `asset` 表也完全可行，但拆开的理由是**访问模式差异**：

- `asset` 表被高频读（列表、详情、统计），但**几乎从不读向量列**
- 向量列有 512 个 `NUMERIC`，单行体积大，全表扫描时会显著放大 I/O
- 向量只在 `analyze` 时写入一次，之后只读

1:1 垂直拆分让"表变窄、行变小"，主表扫描更快。这是典型的**用范式换性能**的取舍——严格说拆分后仍是 3NF，但拆分的动机不是范式要求而是物理设计。代价是关联查询多一次 JOIN，这个代价在高频路径上可以忽略（因为高频路径根本不查向量）。

#### 3.1.3 索引设计：每个索引都对应一条真实查询

项目共 14 个索引，**没有一个是"感觉可能有用"加的**。举三个有代表性的：

**部分索引（Partial Index）**
```sql
CREATE INDEX idx_asset_pending ON asset (created_at DESC)
    WHERE audit_status = 'pending';
```
专家工作台只查待审资产。待审资产在全表中永远是少数（终审后即离开该状态），全表索引会浪费大量空间在已终审行上。部分索引只索引"当前待审"的行，索引体积小一个数量级，命中更快。

**HNSW 向量索引**
```sql
CREATE INDEX idx_public_motif_hnsw ON public_motif
    USING hnsw (base_vector vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
```
`m=16` 控制图的连通度（每层最大连接数），`ef_construction=64` 控制建图时的候选队列大小。两者都在"召回率 vs 构建时间/内存"之间取平衡。`vector_cosine_ops` 使索引与 `<=>` 余弦距离运算符匹配，这样 `ORDER BY base_vector <=> query` 才能走索引。

这里有一个必须说清的坑：**表只有 3 行时，查询规划器会认为顺序扫描比走 HNSW 更便宜**，于是索引被忽略。所以项目在检索前显式 `SET LOCAL enable_seqscan = off` 强制走索引，目的不是提速（3 行数据提速无意义），而是让 `EXPLAIN` 能看到 `Index Scan using ..._hnsw` 这一证据。这个设置在文档中明确标注为"演示期措施，生产环境应去掉"。

**部分唯一索引（保证业务唯一性）**
```sql
CREATE UNIQUE INDEX uq_license_exclusive ON license_record (asset_id, licensee_id)
    WHERE status = 'active';
```
业务规则是"同一资产对同一被授权方的有效独占授权只能有一条"，但历史上失效的授权记录允许多条（用于留档）。这种"在子集上唯一"的需求，普通 UNIQUE 约束表达不了，必须用部分唯一索引。

#### 3.1.4 触发器：7 个，各司其职

| 触发器 | 时机 | 职责 |
|---|---|---|
| `trg_asset_right_change` | AFTER INSERT/UPDATE/DELETE on `asset` | **核心审计**：`right_level`/`audit_status`/`motif_id`/`owner_id` 任一变更时写 `system_audit_log`，含新旧 JSONB 快照 |
| `trg_asset_touch` | BEFORE UPDATE on `asset` | 自动维护 `updated_at` 与 `version_no`（乐观锁版本号） |
| `trg_syslog_immutable` | BEFORE UPDATE/DELETE on `system_audit_log` | 抛异常，审计日志防篡改 |
| `trg_audit_record_no_delete` | BEFORE DELETE on `audit_record` | 禁止物理删除审核流水 |
| `trg_audit_record_guard` | BEFORE UPDATE on `audit_record` | 已终审的记录禁止再改；`pending` 状态迁移放行 |
| `trg_license_no_delete` | BEFORE DELETE on `license_record` | 授权记录只失效不删除 |
| `trg_motif_vector_norm` | BEFORE INSERT/UPDATE on `public_motif` | 向量入库前强制 L2 归一化，避免脏向量污染检索 |

`trg_asset_right_change` 的实现值得展开。它**不是简单地无条件记录每次 UPDATE**，而是逐列用 `IS DISTINCT FROM` 比对，收集真正变化的列名：

```sql
IF NEW.right_level  IS DISTINCT FROM OLD.right_level  THEN v_changed := v_changed || 'right_level';  END IF;
IF NEW.audit_status IS DISTINCT FROM OLD.audit_status THEN v_changed := v_changed || 'audit_status'; END IF;
IF NEW.motif_id     IS DISTINCT FROM OLD.motif_id     THEN v_changed := v_changed || 'motif_id';     END IF;
IF NEW.owner_id     IS DISTINCT FROM OLD.owner_id     THEN v_changed := v_changed || 'owner_id';     END IF;

IF array_length(v_changed, 1) IS NULL THEN
    RETURN NEW;   -- 只改了标题/描述这类元数据，不写业务审计日志
END IF;
```

用 `IS DISTINCT FROM` 而非 `<>` 的原因：如果某列是 NULL，`NULL <> NULL` 结果为 NULL（既不是真也不是假），条件判断会漏掉。`IS DISTINCT FROM` 把 NULL 当普通值比较，语义正确。

"只对权属类字段留痕"这个过滤同样重要——否则用户每改一次标题描述都会产生一条审计日志，日志被噪音淹没，真正的权属变更反而找不出来。

#### 3.1.5 三个视图：让"正确但复杂"的查询只写一次

| 视图 | 用途 | 技术要点 |
|---|---|---|
| `v_asset_pending_audit` | 专家工作台数据源 | `LEFT JOIN LATERAL` 为每行资产取"最新一条 pending 流水"，同时把 `similarity_json` 里的 top1 母题名与相似度展开成列 |
| `v_asset_trace_chain` | 溯源链路 | 用 `UNION ALL` 把"资产登记 / 审核决策 / 授权流转 / DB 自动审计"四类事件归一成 `(event_type, occurred_at, description, snapshot)` 的统一形状 |
| `v_asset_ledger` | 监管台账 | 一资产一行，用 `LEFT JOIN LATERAL` 聚合授权数量与金额，用标量子查询统计审计痕迹数与衍生作品数 |

视图的价值在这个项目里特别明确：**这三个查询都是多表关联 + 聚合 + 窗口逻辑，任何一个应用端实现都容易出错，且一旦逻辑变化要改多处。** 视图把"正确版本"固化在数据库里，应用层只写 `SELECT * FROM v_xxx`。

`v_asset_ledger` 里有一个字段值得注意：

```sql
(a.ai_suggest_level IS NOT NULL AND a.ai_suggest_level = a.right_level) AS ai_expert_agree
```

这一列直接输出"AI 建议与专家结论是否一致"，监管方可据此统计 AI 与专家的一致率。项目截图中台账页的"AI 与专家一致率"卡片就是基于这一列聚合出来的（截图显示 0%，因为演示流程中专家故意推翻了 AI 建议）。这个设计让"AI 是否可信"变成可量化的运营指标，而不是一个说法。

#### 3.1.6 权限：数据库层 GRANT，而非应用层 if

这是全项目设计上最硬的一环。三个角色加一个服务账号：

```
ich_app      应用服务账号，后端以它连接数据库（表的 owner）
ich_heritor  传承人：只能看自己的资产，能上传、能申请审核
ich_expert   专家：可读全部资产，可写审核流水，★只有它能改 right_level
ich_admin    监管方：全量只读 + 可管母题库
```

关键的两条 GRANT：

```sql
-- 传承人可更新的列，★明确不含 right_level
GRANT UPDATE (title, description, file_path, file_hash, file_size, mime_type,
              audit_status, ai_suggest_level, ai_confidence, ai_model_version, motif_id)
    ON asset TO ich_heritor;

-- 只有专家能改权属结论
GRANT UPDATE (audit_status, right_level, motif_id) ON asset TO ich_expert;
```

注意这是**列级 GRANT**，不是表级。PostgreSQL 的列级权限让"传承人能改标题但不能改权属"这件事由数据库自己执行。

运行时机制是：后端统一用 `ich_app` 建连接池，每个请求在事务内 `SET LOCAL ROLE ich_heritor`（或 expert/admin）。`SET LOCAL` 的作用域仅限当前事务，事务结束自动复位，所以连接池中的连接归还后不会带着上一个用户的角色——这是一个容易踩的坑，用错 `SET ROLE` 会导致角色泄漏到后续请求。

### 3.2 AI 模块：特征提取与分级建议

#### 3.2.1 三档特征后端与自动降级

特征提取封了三档实现，按 `ICH_FEATURE_BACKEND` 选择：

| 后端 | 方法 | 依赖 | 维度 |
|---|---|---|---|
| `clip` | open_clip ViT-B/32 图像编码器 | torch + open_clip | 512 |
| `resnet` | ResNet-50 去分类头 + 全局平均池化，2048 维用固定种子随机正交投影降到 512 | torch + torchvision | 512 |
| `builtin` | 纯 numpy 手工特征 | 仅 numpy/Pillow | 512 |
| `auto` | 依次尝试 clip → resnet → builtin | — | — |

统一 512 维不是巧合：ViT-B/32 的 projection dim 正好是 512，与数据库 `VECTOR(512)` 天然对齐，无需降维（降维会损失信息）。三个后端产出同维度向量，意味着**换后端不需要改表结构**，只需接受"历史向量与新向量不可直接比较"——这也是为什么 `model_version` 必须与向量一起落库。

`builtin` 后端不是凑数的玩具，它的设计针对纹样类图像：

```
[0:192)    HOG-lite 方向梯度直方图（6×6 网格 × 8 方向）
           → 捕捉线条走向：回纹的直角折线、缠枝的连续曲线
[192:384)  HSV 色度直方图（4×4 空间块 × H4×S4）
           → 只取色相/饱和度，对曝光差异鲁棒：苗绣靛蓝、青花钴蓝
[384:512)  多尺度 Laplacian 纹理能量（8 个尺度）
           → 捕捉疏密程度：细密苗绣 vs 简洁回纹
```

三段加权拼接的权重 `0.51 / 0.23 / 0.26` 不是拍脑袋定的，而是由 `tests/tune_weights.py` 做网格搜索标定，目标函数是同时满足"翻拍稳定性 ≥ 0.90"（同一作品不同拍摄应判为同一件）与"改编相似度 < 0.92"（改编作品不应被判为公有母题）这两个约束。这个脚本保留在仓库里，标定过程可复现。

#### 3.2.2 分级器：把相似度翻译成建议

`app/ai/classifier.py` 是一个**纯函数模块**，输入 `SimilarityHit` 列表，输出 `Suggestion` 数据类。分级规则：

设 `s` = 与最相似公有母题的余弦相似度：

| 区间 | 建议级别 | 依据 |
|---|---|---|
| `s ≥ 0.92` | `public` 公有母题 | 与传统母题高度重合，属公有领域，不得个人独占 |
| `0.80 ≤ s < 0.92` 且 ≥2 个母题落入该区间 | `derived` 改编衍生 | 与多个公有母题有实质重合，享有演绎著作权但须标注血缘 |
| `0.80 ≤ s < 0.92` 但仅 1 个母题 | `derived`（置信度 ×0.9） | 存在明显借鉴但不构成整体复制 |
| `s < 0.80` | `original` 原创作品 | 未发现与现存公有母题的实质重合 |

另有一条前置检查：若与**已有私有资产**相似度 ≥ 0.95，说明可能是抄袭他人作品，此时标记 `flagged_as='duplicate'`，不参与常规分级，直接交由专家人工核查。

置信度 `conf` 的构造值得一提——它不是硬编码常数，而是两个因子的乘积：

```
margin     = 到最近阈值的距离（越远越自信）
separation = top1 与 top2 相似度的差（越大说明越不被并列候选干扰）
conf       = squash(margin × 8.0) × squash(separation × 6.0 + 0.35)
```

这个设计的意义是：当一张图恰好压在 0.92 边界上，或 top1 和 top2 母题相似度几乎相同时，置信度会自动降低，提示专家"这个结论要仔细看"。相反，一张明显不相似的图会得到高置信度。**置信度在这里不是一个装饰性的百分比，而是"该不该相信 AI"的信号。**

#### 3.2.3 关键约束：分级器不 import 数据库模块

`classifier.py` 的 import 清单只有 `dataclasses`、`app.config`。它**不 import `app.db`、不 import `app.services`**。

这不是随手写的整洁代码，而是刻意为之的架构约束：**从模块依赖图上就断绝了"分级器顺手改一下权属"的可能**。一个模块如果没有数据库连接对象，它在物理上就写不了数据。这条约束由 `tests/test_invariants.py` 静态扫描保证——如果哪天有人给它加了 `from app.db import ...`，测试立刻失败。

#### 3.3.2 终审事务：全系统最关键的 60 行

`services.approve_asset()` 是全系统**唯一**写 `asset.right_level` 的函数。它必须在单个事务内完成 6 步：

```
步骤 1  SELECT ... FOR UPDATE OF a              锁住资产行
步骤 2  状态机校验（只有 pending 可终审）        已 approved → 409
步骤 3  SELECT ... FOR UPDATE 取待审流水        同锁，避免双写
步骤 4  UPDATE audit_record（专家结论）          校验 rowcount == 1
步骤 5  UPDATE asset（right_level + status）    触发器在此写审计日志
步骤 6  回读 system_audit_log 作为触发器生效的证据
```

任一失败整体回滚。

**并发场景推演**（两个专家同时点"通过"）：

```
T1: BEGIN → SELECT FOR UPDATE （拿到行锁）
T2: BEGIN → SELECT FOR UPDATE （阻塞等待）
T1: UPDATE audit_record / UPDATE asset → COMMIT（释放锁）
T2: 拿到锁，读到 audit_status 已是 'approved'
    → 命中状态机校验 → 抛 409 → ROLLBACK
```

结论：不会出现"同一资产被终审两次"，也不会出现"两条终审流水指向同一结论"。这一行为由 e2e 场景 8「并发/幂等保护：重复终审被拒」实测验证。

**为什么用悲观锁而不是乐观锁**（比对 `version_no`）：

- 终审是低频、高价值、人工触发的操作，锁等待成本可忽略（阻塞 100ms 后自然成功）
- 乐观锁失败后要用户重试，体验差

`version_no` 仍然保留自增，用途是台账展示"该记录被改过几次"，而不是并发控制。

**事务与触发器的关系是这个设计中最精妙的地方**：`UPDATE asset` 会触发 `trg_asset_right_change` 写 `system_audit_log`。因为触发器运行在同一事务内，所以：

- 事务 COMMIT → 业务数据 + 审计日志 **一起生效**
- 事务 ROLLBACK → 业务数据 + 审计日志 **一起消失**

这恰好满足"要么同时成功要么回滚"的要求：**不会出现"日志说有变更但数据没变"**。如果审计日志是由应用代码在事务外写，就必然存在这个不一致窗口。

`analyze_asset()` 则相反，它**明确不写 `right_level`**，只写 `audit_record(state='pending')` 与 `asset.ai_suggest_level`。这两个函数的行为差异由不变量测试强制检查。

#### 3.3.3 向量检索的双模式适配

`app/ai/similarity.py` 需要同时工作在两种数据库形态下（详见 3.5 兼容层）。核心设计是**只维护一份 SQL**：

```python
def cast_vec(expr: str = "%(q)s") -> str:
    return f"{expr}::vector" if is_native() else f"ich_to_vector({expr})"
```

SQL 里用 f-string 注入 `cast_vec()` 的结果，两种模式的查询逻辑字面完全一致，只有参数绑定的写法不同。

为什么不用两份 SQL？因为**两份 SQL 长期必然漂移**——今天改了原生版的一个 WHERE 条件，三个月后没人记得降级版也有同样的问题。这才是真正的隐患。用一行函数做适配，代价极小，收益是"永远只有一个事实来源"。

同时 `_apply_vector_settings()` 在降级模式**跳过** `hnsw.ef_search` 等设置——不是疏忽，是必须：降级模式没有 HNSW，而 PostgreSQL 遇到不存在的配置参数会直接报 `unrecognized configuration parameter`，让整个请求 500。

### 3.5 pgvector 兼容层：本项目的额外设计增量

#### 3.5.1 问题

开发环境存在三重限制：系统安全策略禁止执行 `initdb`、无 C 编译器、无 Visual Studio。因此本机**既无法创建 PostgreSQL 实例，也无法编译 pgvector**。

#### 3.5.2 方案

新增 `sql/00_compat_vector.sql`：**不假装有 HNSW，而是换一种等价实现。**

- 向量列类型用 `NUMERIC[]` 冒充 `VECTOR(512)`
- 自定义 `<=>` 运算符（`ich_cosine_distance`）实现余弦距离：
  ```sql
  RETURN 1.0 - (dot / (sqrt(na) * sqrt(nb)));
  ```
- 提供 `l2_normalize` / `vector_dims` / `ich_to_vector` 三个同名或等价函数
- `ich_vector_is_native()` 探测原生扩展，**所有冲突定义都包在 `IF NOT ... END IF` 里**——有 pgvector 时一行都不执行，不与原生运算符冲突

建库脚本用 psql 的 `\if :use_native` / `\else` / `\endif` 切换 DDL（PostgreSQL 10+ 支持条件元命令）。

#### 3.5.3 效果与边界

| 能力 | 原生 pgvector | 降级模式 |
|---|---|---|
| 8 张表 / 约束 / 外键 | ✓ | ✓ |
| 触发器（含审计留痕） | ✓ | ✓ |
| 三个视图 | ✓ | ✓ |
| 列级 GRANT / RBAC | ✓ | ✓ |
| 事务 / 锁 / MVCC | ✓ | ✓ |
| 余弦检索结果 | 近似（HNSW） | **精确（Seq Scan）** |
| `EXPLAIN` 显示 | `Index Scan using ..._hnsw` | `Seq Scan` |

必须如实说明的边界：**降级模式的检索结果比 HNSW 更准（精确排序），但复杂度 O(n)；同时它不能用执行计划证明"HNSW 生效了"**——这条证据只能在装有 pgvector 的环境取得。这个事实写入 README §13.1.1，也在演示模式页面的红色横幅上明示。

### 3.6 演示模式：完整可跑但诚实声明

`app/demo.py`（805 行）是一个**进程内内存存储**，按 8 张表结构组织数据，实现与 `services.py` **同名同签名**的业务函数。

同名同签名这个设计的好处：`api.py` 的 18 个端点只需一行 `fn = demo.xxx if demo.is_enabled() else services.xxx` 切换被调函数，路由、鉴权、校验逻辑零改动。

它明确声明**不生效**的特性（写在文件头，也写在页面横幅上）：

| 特性 | 演示模式下的状态 |
|---|---|
| 列级 GRANT / RBAC | 不生效（数据库权限拦截不会触发） |
| 真实触发器 | 手工模拟，逻辑等价但不是 DB 触发器 |

| HNSW 近似最近邻 | 改为 numpy 全量点积（结果更准，大表更慢） |

模式开关：`ICH_DEMO_MODE=1` 强制演示 / `auto` 自动探测降级（默认） / `0` 强制真库。真实部署应显式设 `0`，避免误以为在跑真库。

## 四、技术方案

### 4.1 技术选型与理由

| 层次 | 选型 | 理由（以及为什么不选替代方案） |
|---|---|---|
| 数据库 | **PostgreSQL 16** | 需要 pgvector（向量检索）、部分索引、列级 GRANT、`LATERAL`、`jsonb`、`FILTER` 子句。MySQL 8 缺少列级 GRANT 与向量索引 |
| 向量扩展 | **pgvector (HNSW)** | 与业务数据同库，无需引入独立的向量数据库（Milvus/Qdrant）。避免"跨库事务"这一根本性难题——权属变更与向量写入必须在同一事务内 |
| 后端框架 | **FastAPI** | Pydantic v2 做请求校验，自动生成 OpenAPI 文档。相比 Flask，类型校验是内建的而非后加的 |
| 数据库驱动 | **psycopg2** + `ThreadedConnectionPool` | 成熟的同步驱动，配合 FastAPI 的 `run_in_threadpool` 使用。不选 asyncpg 是因为 pgvector 类型适配与 `SET LOCAL ROLE` 在 psycopg2 上已验证 |
| 鉴权 | **HS256 JWT，纯标准库实现** | 只用 `hmac` + `base64` + `json`，不引 PyJWT。理由：本项目的 JWT 需求只有签/验，多一个依赖换不来收益 |
| 口令存储 | **pgcrypto `crypt()` + `gen_salt('bf')`** | bcrypt 加盐。在数据库层完成，应用层不接触口令散列 |
| 图像处理 | **Pillow** | 轻量，覆盖 EXIF 矫正、色彩空间转换、缩放 |
| 特征提取 | **numpy（builtin）/ torch（可选）** | 默认零 torch 依赖，保证"pip install 就能跑"；需要更强语义时切 CLIP |
| 前端 | **原生 JS + 单文件 HTML** | 演示场景下无构建、无 node_modules 更可靠 |
| 测试 | **纯 Python 断言脚本** | 不引 pytest，因为需要支持"不装数据库也能跑"的场景 |

### 4.3 关键设计：AI 为什么改不了权属（四层防护）

需求原文是"**明确 AI 只写建议，绝不直接改 `asset.right_level`**"。这个要求如果只靠"我记得别写"，三个月后必然被某次紧急需求打破。所以用四层机制焊死：

**第一层：数据库列级权限（最硬）**

`ich_heritor` 的 UPDATE 权限清单里**没有** `right_level`。即便应用代码写出 `UPDATE asset SET right_level=...`，数据库会抛 `InsufficientPrivilege`，被 `main.py` 的异常处理器转成 403 + "数据库层权限拒绝"。

这不是应用层的 `if role == 'expert'`，而是**数据库自己拒绝**。绕过应用层也绕不过它。

**第二层：源码不变量测试**

`tests/test_invariants.py` 直接扫描源码字符串：

- `analyze_asset` 函数体里不得出现写 `right_level` 的 SQL
- 全工程只有 `approve_asset` 一处出现 `SET right_level`
- `classifier.py` 不得 import `app.db` / `app.services`

共 64 项检查。任何人日后想加一条"AI 自动确权"的捷径，测试立刻红。

**第三层：分级器物理隔离**

`classifier.py` 是纯函数模块，没有数据库连接对象，物理上写不了数据（详见 3.2.3）。

**第四层：写入路径唯一 + 事务留痕**

就算前三层都被绕过，`right_level` 的每次变更都会被 `trg_asset_right_change` 写入 `system_audit_log`（含新旧快照与 `changed_fields`）。而 `system_audit_log` 自己有 `trg_syslog_immutable` 防篡改触发器 + `REVOKE UPDATE, DELETE`。

谁改的、何时改的、从什么改成什么、用什么数据库角色改的——全部留痕，**且改不掉**。

四层的关系是"纵深防御"：第一层挡应用层越权，第二三层挡开发期引入的回归，第四层是最后的事实记录。任何单层失效都不至于让系统失去约束力。

### 4.4 测试策略

无法在真实数据库上执行，是这个项目最大的验证缺口。应对方式是**分层验证 + 负向回归**：

| 测试 | 项数 | 覆盖 | 是否需数据库 |
|---|---|---|---|
| `test_invariants.py` | 64 | 源码级不变量：AI 不写权属、终审单事务、列级 GRANT、日志追加式、XSS 转义、`nz()` 兜底 | 否 |
| `test_compat_vector.py` | 39 | 兼容层：`<=>` 与 pgvector 数值一致（含边界）、归一化后内积=1-距离、`\if` 配对、无裸 `::vector` | 否（纯公式验证） |
| `test_sql_structure.py` | 全部通过 | SQL 静态结构：8 表 3 视图 3 角色、外键目标、触发器函数、关键约束/索引 | 否 |
| `test_classifier.py` | 24 | 分级器四档规则 + 边界 + duplicate 前置检查 | 否 |
| `test_feature_engine.py` | 17 | 特征维度、L2 归一化、翻拍稳定性、不同纹样区分度 | 否 |
| `e2e_demo.py` | 48 | 13 个业务场景端到端，进程内起服务 | 演示模式 |
| **合计** | **192** | | |

**负向回归**是这套测试的关键设计：不是只验证"好代码能通过"，而是**把已知的坏写法放回去，检查必须失败**。项目实际验证了这一点——注入坏代码后检查报 `✗` 并指出具体行号，恢复后全部通过。

这个策略实际抓出了 4 个真实缺陷（见第七章），其中第 3 条完全是由 `test_compat_vector.py` 发现的。

### 4.5 阈值与权重如何确定

**分级阈值 0.92 / 0.80**：这是经验值，来自 builtin 特征在样例纹样上的实测分布——同一纹样不同扫描件相似度通常 >0.90，不同纹样在 0.6~0.8 区间。0.92 略高于"同纹样下限"，留出安全边际；0.80 取不同纹样的上界。

**必须说明这是经验值**，不是统计标定的结果。README §11.1 给出了正式标定方法：在真实非遗图像数据集上画 ROC/PR 曲线找最佳切点。当前阈值让系统可用，但不构成学术意义上的"最优阈值"。

**特征段权重 0.51 / 0.23 / 0.26**：由 `tests/tune_weights.py` 网格搜索得到，目标函数为双约束（翻拍稳定性 ≥0.90 且改编相似度 <0.92）。标定脚本保留在仓库，`features.py` 里写明了"若当前取值无法同时满足两个约束，脚本会以非零码退出并告警"。

## 五、可行性分析

### 5.1 技术可行性

| 维度 | 评估 |
|---|---|
| **依赖成熟度** | PostgreSQL 16 + pgvector 是经过大规模生产验证的组合；FastAPI + psycopg2 组合成熟；Pillow/numpy 无需额外环境 |
| **算法可行性** | 余弦相似度做图像检索是成熟方法。builtin 手工特征对纹样类图像（结构稳定、纹理一致）区分度足够支撑演示；CLIP 在语义层面更强但非必需 |
| **性能可行性** | HNSW 在百万级向量上单查询毫秒级；本项目 3 条母题，降级模式的 Seq Scan 也在 1ms 内。终审事务的 `FOR UPDATE` 锁等待在人工触发频率下可忽略 |
| **已验证部分** | 192 项测试全部通过，其中 48 项为端到端接口测试（业务逻辑真跑过）；8 张真实浏览器截图证明前端可用 |
| **未验证部分** | SQL 脚本未在真实 PostgreSQL 上执行（见 5.4） |

### 5.2 数据可行性

- **母题基准数据的获取**：非遗纹样的公有领域属性明确，可从博物馆公开图录、非遗数字馆等渠道获取。项目提供 `motif_images.py` 程序化生成 3 张测试母题图，验证链路不依赖外部素材
- **数据量级**：一个县域非遗项目的纹样种类通常在百到千级，向量量级不大，单机 PostgreSQL 完全够用
- **数据敏感性**：传承人作品的原始图像有商业价值，需要访问控制。项目实现了"传承人只能看自己的资产"（SQL 层 `owner_id` 过滤，而非取回后判断）

### 5.3 经济与人力可行性

- **软件成本为零**：全部开源组件，无商业授权
- **硬件要求低**：默认后端无需 GPU，普通笔记本可运行；有 GPU 时可选 CLIP 提升效果
- **人力投入**：本次交付为单人完成，约 9800 行代码（含注释与测试）。后续扩展主要成本在数据标注（母题库建设）而非系统开发

### 5.4 主要风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| **SQL 未在真实 PG 上执行** | 可能存在语法/版本兼容问题，导致首次部署失败 | ① 静态结构校验全通过；② 逐行代码审查 + 负向回归；③ 主动发现并修掉 4 个设计缺陷；④ `bootstrap.py` 逐层诊断并给出修复命令；⑤ README §13.1 列出 4 个"可能出问题的位置"及应对方案 |
| **pgvector 版本差异** | HNSW 需 ≥0.5.0，`vector_dims` 需 ≥0.7.0 | 脚本已判断扩展是否存在；README 给出老版本替代方案（降级 ivfflat / 用 `array_length`） |
| **阈值未经真实数据标定** | 分级准确率不确定 | 阈值可配置（环境变量）；README 给出 ROC/PR 标定方法；置信度机制让边界情况自动降权 |
| **builtin 特征无语义能力** | 不能跨模态检索，对大幅旋转不鲁棒 | 明确写入文档作为已接受的取舍；需要时切 CLIP 后端（同维度，不改表） |
| **法律结论边界模糊** | 用户可能把系统建议当法律判决 | 系统全程使用"建议"措辞；AI 结论必须经专家终审才写入权属；文档明确声明"不构成法律意见" |

### 5.5 可行性结论

**技术上可行且已具备可运行形态**。核心链路（上传→检索→建议→终审→溯源）已通过 48 项端到端测试验证业务逻辑正确；数据库设计符合 3NF 并覆盖课程要求的全部要素（约束、索引、触发器、视图、事务、权限）。

**主要缺口是"未经真实数据库执行"这一项**，这是开发环境限制而非设计缺陷。README 已如实声明，并提供三条运行路径（Docker / 已有库 / 降级模式）与逐层诊断工具，把首次部署的风险降到"可定位、可修复"的程度。

## 八、结论

本选题从一个具体的现实问题出发——非遗数字资产在数字化过程中出现的"公有母题被私有化圈占、改编幅度无法量化、权属结论不可追溯"，把它转化为一个可用技术手段部分解决的分级确权问题：**用图像向量相似度作为借鉴程度的客观代理指标，用 PostgreSQL 的约束、触发器、视图、事务与权限体系保证判断过程的规范性。**

项目的技术重点不在算法创新，而在**工程约束的落实**。需求中"AI 只写建议、绝不直接改权属"这一条，如果只写进文档就形同虚设；本项目用四层机制（数据库列级 GRANT、源码不变量测试、模块依赖隔离、触发器留痕）把它变成"物理上做不到"，并且用 192 项测试持续守护这个不变量。

项目目前已交付一个可运行、可演示、有完整测试证据的系统，同时**如实声明了最大的一处验证缺口**——SQL 脚本未在真实 PostgreSQL 上执行。这一声明不是免责，而是把风险显式化：列出 4 个可能出问题的位置、给出对应的修复方案、提供逐层诊断工具。在 4.4 与 7.2 中记录的 4 个主动发现并修复的缺陷，也说明"逐行审查 + 负向回归"这套替代验证手段确实有效。

作为数据库原理课程设计，本项目覆盖了课程要求的核心要素：3NF 与垂直拆分、7 类索引（普通/部分/部分唯一/组合/HNSW/GIN）、7 个触发器（审计/维护/防篡改/守卫/归一化）、3 个视图（含 `LATERAL` 与 `UNION ALL`）、悲观锁与事务原子性、列级 GRANT 与最小权限原则。这些不是"为了覆盖考点而加"，每一条都对应一个真实业务约束的落地需求。
