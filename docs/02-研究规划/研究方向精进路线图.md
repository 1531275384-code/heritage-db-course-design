# 研究方向精进路线图

> 目标：把当前「非遗数字资产分级确权与溯源系统」从**工程成品**，转为**可支撑研究的经济仿真试验台**。
> 定位重心从「非遗」移到「信息不对称下的认证机制」——非遗是载体，认证是研究对象。
>
> 编写日期：2026-11-02

---

## 0. 前提与三条底线

**前提假设**（若与实际不符，P3 的取舍需要重排）：

1. 用途是研究方向延伸／开题，不是单纯课程作业——所以 P3 的实验设计必须立住，不能只到 P1。
2. 现有交付物**不废弃**：`01-交付物/` 的说明书与两个演示页继续有效，只是叙事口径要改。
3. 时间预算按「可断续投入」估计，单项工作量只给相对量级，不给具体日期承诺。

**三条底线**：

- 不重写 `app/`。它就是「机制的形式化 + 真人基线」，是资产不是包袱。
- 不做「第二个 EconGym」。规模差两个数量级，硬拼必输。
- 不宣称没验证过的东西。SQL 至今没在真实 PostgreSQL 上跑过，这条在 P0 解决之前，任何「机制正确」的表述都要加限定。

## 1. 现状一句话

工程完成度高（379 项断言全绿、两份演示页、两套说明书），但**研究属性为零**：没有 agent、没有时间步、没有目标函数、没有重复实验、没有基线对比。现在能回答「系统做出来了没有」，回答不了「换一种机制会怎样」。

## 3. P0：可信度与地基

这一层不产出研究结果，只决定「后面的结果能不能被信」。

### P0-1　定位与叙事统一

- **预期目标**：读者看任何一份材料，都能在第一屏读到「这是一个研究信息不对称下认证机制的项目」，而不是「一个非遗管理软件」。
- **做什么**：
  1. 标题改为正副结构——正标题点研究问题，副标题保留「以非遗数字资产授权为例」。旧名不删，避免与已提交材料冲突。
  2. 在 `docs/` 新增 `研究定位说明.md`：与 EconGym 的差异、为什么它缺「认证者」角色、本项目的边际贡献是什么。
  3. 同步四处口径：`README.md` 首段、Word 说明书第 1 章、两个演示页的 `<title>` 与页头、`docs/01-工程说明书/交付物说明.md`。
- **可衡量标准**：
  - 四处口径的「研究对象」表述完全一致，不含「管理系统」「工具」这类词作为主定位；
  - `研究定位说明.md` 里能明确写出 1 句「别人没有而我有」的差异陈述；
  - 全文检索旧主标题作为**唯一标题**的出现次数为 0（作为副标题保留是允许的）。
- **风险与依赖**：唯一风险是改名导致与已交材料对不上——用正副标题共存规避。无技术依赖，可立刻做。

### P0-2　真实 PostgreSQL 跑通

- **预期目标**：把「列级 GRANT、7 个触发器、CHECK/UNIQUE/外键、HNSW 索引、`FOR UPDATE` 串行化、事务回滚」这 12 项，从纸面变成可复现的执行证据。
- **实施顺序**：
  1. **先做 30 分钟可行性探测**（这一步最关键，别一上来就铺开）：依次尝试 `pip install pgserver`（自带二进制）→ 查找本机已有 `postgres.exe` → Docker。任一成功即进入第 2 步；全失败则当天转入降级方案，不要耗一周。
  2. 建库、执行 `sql/01_init.sql` 与 `02_index_trigger_view.sql`。
  3. 逐条写验收脚本：每个触发器至少构造一次**预期失败**的写入；GRANT 用低权限角色实测 `SELECT` 被拒；`EXPLAIN` 确认走 HNSW；两个并发事务验 `FOR UPDATE`。
  4. 落盘证据：`docs/verify/pg_run.log` + 逐步截图，替换掉原第 7.2 节「10 项待验收」清单。
- **可衡量标准**：
  - 12 项中 ≥10 项有执行日志与结果断言，剩余 ≤2 项必须写明为何无法执行；
  - 每个触发器有「应失败而失败」的反向用例，不是只有正常路径；
  - 一条命令可从空库重建（`make db-reset` 或等价脚本），重复三次结果一致。
- **风险与依赖**：
  - 沙箱可能仍拦 `initdb`；pgvector 需编译，Windows 下易失败。
  - **降级路径**（必须预先写好，不要临场决定）：无 pgvector 时用 `cube` 扩展或数组 + 手写距离函数模拟，并在文档中显式标注「向量索引未实测」；完全无法起库时，用 SQLite 做语义等价检查，并保留原有限定语。
  - 无上游依赖，但如果失败，P0-3 的保真度验证会一起降级。

### P0-3　规则单一真相

- **当前状态**：步骤 1、2、3 已完成（第 11、12、13 节），步骤 4 已补做对拍红灯验证（`--self-check`）。
  步骤 1 之后新发现 1 条同类漏洞（传承人可自行终审定级），已作为「步骤 1b」列入第 13 节。
- **预期目标**：机制约束只写一次。SQL 改了而 Python 没跟上时，测试必须变红。
- **做什么**：
  1. 写提取器：从 `01_init.sql` 解析 CHECK / UNIQUE / 外键 / 触发器条件，生成 `sim/rules.py` 的常量表（不是手抄）。
  2. 建 `tests/test_rules_parity.py`：构造 N 组边界状态，同一状态分别喂真实数据库与 Python 规则，比对判定结果。
  3. 做一次「故意不同步」实验：只改 SQL 不改 Python，确认测试失败——**验证测试本身有效**。
- **可衡量标准**：
  - 边界状态样本 ≥40 组，覆盖三档分级的两个阈值、四种授权类型、状态机的非法跃迁、「未终审即授权」「自己授权给自己」；
  - 一致率 100%，不一致时输出可读差异（哪条规则、哪个字段）；
  - 故意不同步实验能稳定复现红色。
- **风险与依赖**：触发器（BEFORE/AFTER、行级/语句级）语义翻译容易出错，建议只翻译**约束性**触发器，审计类触发器不进 `rules.py`。硬依赖 P0-2。

## 4. P1：仿真内核最小可用

这一层做完，项目才第一次具备「换个参数再跑一遍」的能力。

### P1-1　仿真内核骨架

- **预期目标**：`RightsMarketEnv` 能 `reset()` 出一局、`step()` 推进一期，产出结构化轨迹。
- **实施顺序**：定义「一期」→ 定四类角色的 obs/action/reward → 写 env → 接 runner。
- **可衡量标准**：
  - `python -m sim.runner --scenario baseline --seeds 1` 产出 `trajectory.parquet`，含 `t / agent_id / role / action / reward / state_hash`；
  - 通过 `gymnasium.utils.env_checker.check_env`；
  - 8 件作品 × 20 期，单 seed 端到端 < 2 秒；
  - 同 seed 两次运行 `state_hash` 序列完全一致（确定性）。
- **风险与依赖**：
  - **最大的设计风险**：原业务没有时间维度，硬加「期」会显得牵强。建议把「一期」定义为一次完整循环（申报 → 预筛 → 复核 → 授权 → 到期），并让授权到期（`end_date`）天然成为跨期事件，这样时间轴有业务含义而不是凭空造。
  - 依赖 P0-3。

### P1-2　规则基线搬运

- **预期目标**：`policies/rule.py` 复刻现有 `app/services.py` 的判定，作为所有学习型策略的对照组。
- **可衡量标准**：
  - 对 8 件种子作品，rule policy 输出的档位与 `seed_demo.json` 里真实 `audits` 100% 一致；
  - `scripts/check_seed.py` 的 AI 结论回算仍全部吻合（不能因为搬逻辑而漂移）；
  - 现有 379 项断言保持全绿。
- **风险与依赖**：现有逻辑里混了数据库访问，需先抽纯函数。依赖 P1-1。

### P1-3　指标定义与四基线

- **预期目标**：第一次能回答「四种审核策略哪个好」，而不是「系统能跑」。
- **指标（6 个）**：总福利、争议率、档位通胀率（申报档位均值 − 专家核定档位均值）、专家利用率（复核数 / 预算）、逆向选择指数（高相似度作品的成交占比）、授权费集中度（Gini）。
- **四基线**：全审、全不审、随机抽、按 AI 置信度抽。
- **可衡量标准**：
  - 同一 seed 下四基线指标可复现，两次运行数值完全相同；
  - 输出一张对比表 + 一张折线图，能看出「全审 vs 按置信度抽」的差距方向；
  - 每个指标在文档里有定义式与文献口径出处，不是自己拍脑袋命名。
- **风险与依赖**：指标定义最容易被质疑，宁可少而准。依赖 P1-2。

### P1-4　YAML 场景配置

- **预期目标**：换实验不改代码。
- **可衡量标准**：
  - 至少 4 个场景：`baseline` / `scarce_expert`（专家预算砍半）/ `gaming`（传承人可策略性申报）/ `market_power`（存在大买方）；
  - 切换 `--scenario` 后角色数、算法指派、预算随之变化，日志可验证；
  - 配置用 pydantic 校验且 `extra="forbid"`——**这是历史踩过的坑**：v2 会静默丢弃未声明字段，导致配了不生效。
- **风险与依赖**：依赖 P1-1；可与 P1-2／P1-3 并行。

## 5. P2：结构性缺口

这一层才让「多智能体」和「群体决策」从标签变成事实。

### P2-1　专家 1→N 与聚合

- **预期目标**：同一作品由多名专家独立定级，按规则聚合，并识别分歧。
- **聚合三选**：多数票、置信度加权、声誉加权（声誉由历史准确率内生更新）。
- **可衡量标准**：
  - 三种聚合可切换，同一输入产出可比结果；
  - 构造「3 专家 2:1 分歧」用例，系统能标记分歧并触发二次复核；
  - 输出「单专家 vs 多专家」的争议率对比，差异有方向性解释。
- **风险与依赖**：需要改 schema（`audit` 加「同一作品同一专家唯一」约束），会牵动 P0-3 与现有测试，改动面比看起来大。声誉权重没有真实数据，只能是仿真内生，文档里要说明这一点。

### P2-2　被授权方 agent 化

- **预期目标**：`licensee_name` 这个字符串变成有预算、有保留价、能在四种授权类型间选择的行动者。
- **可衡量标准**：
  - 买方按保留价决策，成交价 ≤ 保留价的约束在全部轨迹中成立；
  - 独占授权造成的垄断损失可被计算并单独报表；
  - 市场出清率、平均成交价、四种类型的分布三项指标可输出。
- **风险与依赖**：新增表与字段，是全部改动里最大的一次 schema 变更；建议先加「影子表」跑通再迁移正式表。依赖 P0-3。

### P2-3　RL 策略接入（PPO）

- **预期目标**：至少一个角色（建议监管：定阈值与配额）由 PPO 学习。
- **可衡量标准**：
  - 在 `scarce_expert` 场景下，3 个 seed 均值相对 rule baseline 的总福利提升 ≥5%，并报告置信区间；
  - 学习曲线落盘可复现（固定 seed 重跑一致）；
  - 若提升不足 5%，必须给出「为什么学不动」的诊断（动作空间太离散／奖励太稀疏），不能只报数字。
- **风险与依赖**：小规模多智能体上 PPO 常不收敛，先跑通再谈提升。依赖 P1-3。

### P2-4　LLM 策略接入

- **预期目标**：至少一个角色（建议传承人）由 LLM 扮演，产出自然语言申报理由，供专家侧阅读。
- **可衡量标准**：
  - `temperature=0` 时同一输入决策可复现；
  - 有调用缓存层，重跑不重复计费，缓存命中率可观测；
  - LLM 决策与 rule baseline 的偏离度可量化（用于论证「LLM 不等于随机」）。
- **风险与依赖**：成本与不稳定性是主要风险，务必先做离线批量 + 缓存，不要在线逐条调。依赖 P1-3。

## 6. P3：研究增量

### P3-1　RQ1 配额分配

- **问题**：给定专家每期只能复核 k 件，AI 预筛 + 人工抽检怎么配最优？
- **可衡量标准**：在 k ∈ {0, 25%, 50%, 100% 预算} 四档下，给出「争议率—福利」的帕累托前沿；能指出一个反直觉结论（例如「按置信度抽反而比随机抽更差」若成立）。
- **依赖**：P1-3。

### P3-2　RQ2 策略性行为

- **问题**：AI 给置信度后，传承人会不会把申报卡在阈值附近？专家推翻率会不会被 AI 建议锚定？
- **可衡量标准**：申报分数在阈值 ±0.05 区间的密度显著高于其他区间（给出检验）；专家在「AI 建议与自身判断不一致」时的推翻率，与「无 AI 建议」对照组比较有显著差异。
- **依赖**：P2-3、P2-4。

### P3-3　RQ3 福利分解

- **问题**：认证精度提升是否缓解逆向选择？独占授权的垄断损失多大？
- **可衡量标准**：总福利分解为「创作者剩余 + 被授权方剩余 − 争议成本」三项，三项随认证精度变化的曲线齐备且闭合（残差 < 1%）。
- **依赖**：P2-2。

## 8. 建议不做的事（负向清单）

这五件事看起来诱人，但现在做会稀释主线：

1. **重写 `app/`** —— 它是机制规格与真人基线，重写等于自断两条腿。
2. **做通用经济仿真平台** —— 打不过 EconGym，且与本项目的制度细节优势相悖。
3. **急着扩数据集** —— 8 件作品的问题不在数量，在「没有外部效度」；先立机制，扩数据放到 P3 之后。
4. **让 LLM 当主角** —— LLM 是策略库里的一个选项，不是研究问题本身。把 LLM 写进标题会显得没有经济学内核。
5. **在 P0-2 之前宣称机制正确** —— 一被追问「跑过吗」就崩。

## 9. 全局风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 真实 PG 起不来 | P0-2/P0-3 降级，机制证据打折 | 30 分钟探测 + 预设降级路径，当天决策不拖延 |

| 时间维度牵强 | 仿真被质疑「为了做而做」 | 「一期 = 一次完整业务循环」，用授权到期做跨期锚点 |

| LLM 成本失控 | 实验跑不完 | 离线批量 + 缓存 + 固定样本集 |

## 11. P0-3 步骤 1 执行记录：把「未终审不得授权」下沉到数据库（2026-11-08）

### 做了什么

在 `02_index_trigger_view.sql` 增加 B3b 区块，给 `license_record` 挂 BEFORE INSERT 触发器
`trg_license_require_approved`，按 `asset.audit_status = 'approved'` 判定；`rejected` 与 `draft` 一视同仁地拒绝。

只挂 INSERT、不挂 UPDATE：授权记录是追加式的，`status` 允许 `active → expired/revoked` 的收尾迁移，
那不改写「当初这次授权是否合法」。若在 UPDATE 上也查当前状态，资产状态日后变化会误伤历史记录的正常收尾。

不做 `SELECT … FOR UPDATE`：asset 的状态机是 `draft → pending → approved` 且 approved 后不允许回退，
「读到 approved 又被改回 draft」这条竞态在实际数据流里不存在，加锁只是给授权登记引入无意义的等待。

### 实测结论

| 场景 | 结果 |
|---|---|
| `audit_status = 'draft'` 插授权 | 拒绝（23514） |
| `audit_status = 'rejected'` 插授权 | 拒绝（23514） |
| `audit_status = 'approved'` 插授权 | 放行（license_id 正常返回） |
| 种子数据 5 笔授权全部重灌 | 全部通过，无一条被误伤 |

第三条是关键：没有它，「拒绝」可能只是触发器一律拒绝造成的假阳性。

### 但这一步顺带炸出了 5 个更严重的缺陷

补约束后为了验证「合法路径没被误伤」，第一次真正在真库上跑完整链路，结果连续撞墙：

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 4 | 触发器里 `v_changed := v_changed \|\| 'right_level'` | `TEXT[]` 被当成 `text[]` 匹配数组拼接重载，**任何 `UPDATE asset` 都抛 malformed array literal**，包括专家终审 | 改用 `array_append` |
| 5 | `db.healthy()` 把「无 pgvector」判为不可用 | 完全可用的降级库被误判，`init_seed` / `check_seed` 直接拒绝执行，与 `bootstrap.py` 的四层探测结论互相矛盾 | 改三态：原生 / 兼容层 / 都没有 |
| 6 | `license_record` 三个角色都只有 SELECT | **没有任何角色能 INSERT**，「登记授权」在真库上必然 42501 | 给 heritor 与 admin 补 `GRANT INSERT`，仍不给 UPDATE/DELETE |
| 7 | `init_seed.py` 用 `ich_admin` 写资产；清理逻辑假设外键是 CASCADE | admin 无 asset 写权限；实际外键是 RESTRICT，且子表有禁删触发器，旧数据根本删不掉 | 初始化走超级用户；清理按子表→父表并临时 `session_replication_role = replica`；补齐缺失的 `heritor02` 账号并校准序列 |

第 4、6、8 条是同一个主题：**「权限收紧」与「触发器代写」必须配套**。
只收紧权限不给代理，功能就死了；只给代理不收紧，审计就可伪造。
现在的组合是：审计触发器 `SECURITY DEFINER` + 固定 `search_path`，业务角色对 `system_audit_log`
依然只有 SELECT —— 既跑得通，也伪造不了。

## 12. P0-3 步骤 2 执行记录：规则表自动生成与对账（2026-11-08）

### 做了什么

新增 5 个文件，`sim/` 目录第一次有了实质内容：

| 文件 | 性质 | 作用 |
|---|---|---|
| `sim/ruleast.py` | 手写 | 规则表达式 AST + 三值逻辑求值器 |
| `scripts/gen_rules.py` | 手写 | 从 SQL 解析并生成规则表；`--check` / `--verify-db` |
| `sim/rules.py` | **自动生成** | 24 CHECK / 4 UNIQUE / 12 外键 / 53 NOT NULL / 8 触发器 |
| `sim/verdict.py` | 手写 | 行级与操作级判定（含触发器三类语义） |
| `tests/test_rules_sync.py` | 手写 | 54 项：漂移、覆盖、语义 |
| `scripts/probe_drift.py` | 手写 | 故意制造不同步，验证检测真的会失败 |

### 三个关键设计决策

**一、解析不了就抛错，绝不跳过。**
`CHECK` 表达式走一个小型递归下降解析器（or → and → not → primary → predicate → operand），
遇到未登记的函数（如 `now()`）或不支持的操作符（如 `IS DISTINCT FROM`）直接抛 `ExtractError`。
「猜一个近似语义」比「明确报错」危险得多：近似语义会安静地跑出错误结论。
同理，出现一个没有语义签名的触发器函数时，生成直接失败 —— 新增触发器必须有人确认它属于哪类规则。

**二、约束性触发器用「签名匹配」，审计类不进规则表。**
plpgsql 图灵完备，没有通用解析办法。这里对每个函数声明若干必须命中的正则，
并且**表名、事件、列名、允许状态都从 SQL 里抓出来**，声明的只是「这段代码属于哪一类判定」。
函数体一改，签名不命中，生成失败 —— 这比手抄多一层强制复核，又不必假装能解析任意 PL/pgSQL。

分类结果：`reject` 3 / `gate` 1 / `guard` 1 / `derived` 2 / `audit` 1。
只有前三类参与接受/拒绝比对，后两类登记在案以防新触发器无人审阅。

**三、与真实库对账，才是真的防漏。**
`--check` 只能发现「改了没重新生成」，发现不了「解析器漏抽了一条」。
`--verify-db` 用 `pg_constraint` / `pg_indexes` / `pg_trigger` / `information_schema.columns`
反查实际存在的约束，与生成结果逐条比对（按 表+名字 集合比较，不是只比数量）。
本次结果：CHECK 24/24、UNIQUE 3/3、部分唯一索引 1/1、外键 12/12、触发器 8/8、NOT NULL 53/53，**全部一致**。

### 比原计划扩了口径

原计划只解析 CHECK / UNIQUE / 外键。实际必须加上三类，否则规则表会系统性偏松：

- **NOT NULL**（53 条）：最容易漏，因为它不写在任何 `CONSTRAINT` 里；
- **长度上限**（`VARCHAR(n)` / `CHAR(n)`）：违反时报 22001 而非 23514，「不是 CHECK 所以不算规则」是错觉；
- **枚举取值域**（3 个 `CREATE TYPE … AS ENUM`）：非法值报 22P02，同样不是 CHECK。

### 实测结论

- 生成：`python -m scripts.gen_rules` → 24 / 4 / 12 / 8 / 53，与手工盘点完全一致；
- 对账：`--verify-db` 六类全部一致；
- 测试：`tests.test_rules_sync` **54 项通过 / 0 失败**；
- 机制自证（`scripts/probe_drift.py`）：加一条 CHECK 不重新生成 → 退出码 1 并给出差异；
  改掉「`v_status <> 'approved'`」这个判断 → 退出码 2，报「函数体与声明的语义不再匹配」。还原后 `--check` 回到 0。
- 全量回归：**12 套 / 468 项 / 1 缺口 / 0 失败**（原 11 套 / 414 项）。

**这两次失败才是本轮最重要的产出**：它证明检测不是摆设。测试从不失败，等于没有测试。

### 踩到的坑（如实记录）

`probe_drift.py` 第一版用 `read_text` / `write_text` 还原 SQL，Windows 的换行符转换把
`01_init.sql` 里原本混用的 LF 统一成了 CRLF —— 内容没变，但文件指纹变了，`--check` 因此误报。
定位方式是看差异：**只有指纹那一行不同**，说明语义没变。改用 `newline=""` 按字节读写后，
还原后指纹逐一校验通过。教训：任何「读—改—还原」的实验都要按字节做，不能用文本模式。

### 对步骤 3 的影响

1. **对拍的对象明确了**：不是「整行 INSERT 能不能成功」，而是拆成三层 ——
   行内规则（NOT NULL / 长度 / 枚举 / CHECK）、触发器（reject / gate / guard）、
   以及本模块**故意不判**的 UNIQUE / 外键（取决于库里已有行，只能靠真写一次看是否被拒）。
   第 2 层与第 3 层必须在样本里分开，否则一处失败分不清是哪边错了。
2. **三值逻辑是最可能出错的地方**：`end_date IS NULL OR end_date >= start_date`
   在 `end_date` 为 NULL 时是 UNKNOWN，SQL 视为通过；用 Python 的 `or` 直译会得到 `False` 或抛 TypeError。
   对拍样本必须显式覆盖「NULL 落在成对约束里」的情况。
3. **样本里必须有「以业务角色执行」的用例**：上一轮 8 个缺陷有 5 个只在换角色时暴露，
   全用超级用户跑等于没测权限边界。

## 13. P0-3 步骤 3 执行记录：对拍测试（2026-11-08）

### 做了什么

新增 `tests/test_rules_parity.py`：同一组边界样本，一边真写进 PostgreSQL，一边喂 `sim/verdict`，
比「接受 / 拒绝」是否一致。**75 组样本，分四层**：

| 层 | 组数 | 说明 |
|---|---|---|
| 规则对拍 | 62 | 行内规则 + 触发器语义，两侧都判，必须 100% 一致 |
| 权限边界 | 7 | Python 规则模型不管 GRANT，只核对库按预期拒绝 |
| 唯一性与外键 | 6 | 依赖库里已有行，Python 有意不判，只靠真写一次确认 |
| 已知缺口 | 2 | 两侧都不拦，只报事实，不计入一致率 |

覆盖率按路线图要求逐条核对：三档取值的两个边界（`ai_confidence` 0 / 1 与三种 `right_level`）、
四种授权类型、审核状态机非法跃迁（approved → pending、rejected → 重判）、未终审即授权（draft / pending / rejected 三种父状态）、
自己授权给自己、成对约束的 NULL 分支。**一致率 62/62 = 100%。**

### 第一个真问题：Python 少了一层类型转换

对拍第一次跑就红了 4 组，全部同一原因：**PostgreSQL 在 CHECK 之前会先把值转成列的存储类型，这个转换会改变数值。**

```
ai_confidence = 1.00004  →  存成 1.0000  →  `<= 1` 成立  →  放行
fee_cny      = -0.004    →  存成 -0.00   →  `>= 0` 成立  →  放行
version_no   = -0.4      →  存成 0       →  `>= 0` 成立  →  放行
```

Python 直接拿原始值判，这四条就全部判反。修法是在 `sim/verdict.py` 里加 `coerce_value()`：
按 `COLUMN_TYPES` 把 `NUMERIC(p,s)` 四舍五入到 s 位、把浮点型整数列取整，**先转换再求值**。

这不是「为了让测试变绿而改代码」——判据是独立的：库的实际行为是事实，Python 是模仿者，
模仿得不对就该改模仿者。反证也做了：关掉 `coerce_value`，同样 4 组立刻变红；打开则全绿。
这条语义同时补进离线测试（`test_rules_sync` 增 5 项），不依赖数据库也能守住。

### 第二个发现：一条比「未终审不得授权」更直接的漏洞

写样本时需要先确认「传承人能不能自己把作品置为已终审」，探针结果：

```
SET LOCAL ROLE ich_heritor;
INSERT INTO asset(..., right_level='original', audit_status='approved')  →  成功
UPDATE asset SET audit_status='approved' WHERE asset_id=900001           →  成功
```

**数据库层没有任何拦截。** 传承人对 `audit_status` 本来就有 UPDATE 权限（提交时要用），
但权限只限制「能改哪一列」，不限制「能改成什么」。结果是：不需要专家，传承人自己就能完成终审定级，
而「终审必须由专家完成」这条业务规则只写在 `app/services.py` 里。

这是和步骤 1 完全同类的漏洞：**权限收紧与状态机约束是两件事，只做前者不够。**
另外 `01_init.sql` 里 `ck_asset_ai_pair` 上方的注释写着「状态为 approved 时 right_level 必须已被显式设置」，
但该约束实际只校验 AI 字段成对，注释描述的行为并不存在——注释与实现不符，比没有注释更危险。

已作为 **步骤 1b** 记录，修法明确：`BEFORE INSERT OR UPDATE` 约束触发器，
`NEW.audit_status IN ('approved','rejected')` 时要求调用方角色为 `ich_expert`（角色从 `current_setting('role')` 取，
沿用步骤 1 已验证的取值方式），种子与运维走超级用户不受影响。
这两条缺口已写成常驻探针，每次跑对拍都会打印，不会只躺在文档里。

### 第三个发现：有些规则根本不在数据库里

三档分级的两个阈值（`SIM_PUBLIC_THRESHOLD=0.92`、`SIM_DERIVED_THRESHOLD=0.80`）只存在于
`app/config.py` 与 `app/ai/classifier.py`，SQL 侧没有任何对应物。所以：

- 对拍覆盖的是**完整性约束**，覆盖不到**分级策略**；
- 这两条阈值目前是「单一实现」而不是「单一真相」——只有一份代码，没有第二份可以对照。

P1-2「规则基线」需要把它们提升为显式配置并纳入场景文件，否则仿真内核会另抄一份阈值，
那就又回到「两处各写一遍」的老问题。

### 验证「这套对拍真的会红」

`--self-check` 会把 Python 侧的置信度上界从 1 改成 0.9999（一次真实的语义偏差，不是伪造结果），
然后重跑全部样本，要求出现不一致：

```
不一致样本数 = 2（期望 ≥ 1）
  · 置信度上界 1
  · 置信度 1.00004（NUMERIC 取整）
✓ 自检成立：对拍能抓住语义偏差
```

加上前一轮的取整反证，两类红灯都验证过了：**改 Python 会红、关掉转换会红。**

### 对拍的能力边界（必须说清）

1. **只能证明两个实现一致，不能证明一致的那个是对的。** 上面那条自审定级漏洞两侧都不拦，
   对拍会安静通过——所以缺口探针必须单列，不能用「100% 一致」替代正确性论证。
2. **唯一性与外键无法在 Python 侧判定**，因为它取决于库里已有哪些行、以及并发事务。
   这类规则只能靠真写一次确认，本文件把它们放在独立层，不混进一致率。
3. **判定只看接受/拒绝，不看报错码。** 同一条数据可能先被触发器拦、也可能先被 CHECK 拦，
   这属于实现顺序；但「库收不收」不含糊。
