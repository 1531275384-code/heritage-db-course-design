## 四、过程中发现的错误与异常

### 4.1 已修复的真实缺陷

#### 缺陷 A：溯源节点序号乱序（`seq_no` 语义错位）

**现象**：第一次跑完，溯源时间轴渲染成

```
1. 资产登记
4. DB 自动审计：-
4. DB 自动审计：audit_status
2. 专家终审通过
4. DB 自动审计：right_level,audit_status
3. 独占授权
```

序号是 **1 → 4 → 4 → 2 → 4 → 3**，看上去像时间轴坏了。

**根因**：`v_asset_trace_chain` 视图里的 `seq_no` 是**按事件类型写死的常量**：

```sql
SELECT a.asset_id, 1::smallint AS seq_no, ... 'root'        -- 节点1
UNION ALL
SELECT ar.asset_id, 2::smallint,           ... 'audit'       -- 节点2
UNION ALL
SELECT l.asset_id,  3::smallint,           ... 'license'     -- 节点3
UNION ALL
SELECT s.record_id, 4::smallint,           ... 'system_log'  -- 节点4
```

它表达的是「**这是第几类节点**」，不是「这是第几步」。但一条链上必然有多个 `system_log`（登记、分析、终审各触发一次），于是三个审计节点全都标 4。**真实库和演示模式两侧写法一致，所以这不是降级造成的，是真库也会有的问题。**

**修复**：在应用层按实际发生时间重编 1..N（`app/services.py` 与 `app/demo.py` 各一处），视图保持「事实投影」的职责不变。同毫秒的节点保留视图原序，保证「业务事件排在其触发的审计快照之前」。

**修复后**：`序号连续性 [1, 2, 3, 4, 5, 6] ✓`

#### 缺陷 B：母题血缘（`asset.motif_id`）从未被回写

**现象**：监管台账的「母题」列，衍生作品也显示 `—`（无血缘）。

**根因**：`sql/01_init.sql:114` 定义了 `motif_id BIGINT -- 关联公有母题(可为空=无母题血缘)`，并有外键 `fk_asset_motif`；`v_asset_ledger` 也 JOIN 了它输出 `motif_code` / `motif_name`。但**分析流程的 `UPDATE asset` 语句里根本没有 `motif_id`**——字段建了、视图用了、生产代码没写。演示模式同样没写，所以两侧都看不出来。

**修复**：判为 `public` 或 `derived` 时，把 Top-1 母题的 id 写入 `motif_id`；判为 `original` 时保持 `NULL`。注意这不改权属，只是记录「AI 认为它源自哪条母题」，专家终审仍可推翻。

**修复后**：衍生作品显示 `母题血缘=MO-001`，原创作品显示 `无`。

## 五、需要注意的地方

### 5.1 这次跑的是演示模式，数据库约束没被验证

本次所有结论都建立在**内存存储**上。以下能力**没有**被这次运行证明：

- 列级 GRANT 是否真的拦住传承人改 `right_level`
- CHECK / UNIQUE / 外键是否真的拒了脏数据
- 触发器是否真的写了 `system_audit_log`（演示模式是**模拟**写的，逻辑对但不是真触发器）
- HNSW 索引是否真的被使用
- 事务回滚是否真的生效

要证明这些，必须在真 PG 上跑：`docker run ... pgvector/pgvector:pg16` 后 `ICH_DEMO_MODE=0 python tests/run_e2e_inline.py`。

### 5.2 样本集中在阈值边界，扩样本时阈值可能要重标

本次两条样本的相似度是 0.9182（衍生）和 0.6036（原创）。0.9182 距 0.92 只差 0.0018 —— 分级器判对了，但**这说明 builtin 后端的相似度分布很挤**。如果加入更多真实绣片，建议：

1. 先跑 `python -m tests.tune_weights` 重新标定 0.51 / 0.23 / 0.26 三段权重
2. 用 20 条以上带标注的样本画一次相似度直方图，看 0.80 / 0.92 这两刀切在哪里最干净
3. 只有在样本量够时才调阈值，不要看到一条擦线就改

### 5.3 置信度不能当"把握程度"读

两条样本的置信度是 0.4372 和 0.7417，都不到 0.8，但判定结果都正确。置信度公式是 `squash(margin×8.0) × squash(separation×6.0+0.35)`，它衡量的是「这条判定离阈值有多远、与其他候选有多分离」，不是「有多准」。**0.44 不代表"四成可能对"**。UI 上已经只作为参考数值展示，不参与决策，答辩时需说明这一点。

### 5.4 演示模式退出即丢

内存数据在进程结束时清空。讲完一遍要再讲，需要重启服务。这也是待办 P1 里「演示数据一键重置」的由来。

### 5.5 上传目录会累积文件

`data/uploads/` 现在有 33 个文件。每次上传都会落盘一份 UUID 命名的副本，同样的图重复上传虽然会命中文件查重（返回 `duplicate_of`），但**首次落盘的文件不会自动清理**。演示无妨，生产需要定期回收或改对象存储。

### 5.6 本次验证的两个修复都改了运行路径，需回归

`app/services.py` 与 `app/demo.py` 都动了。已跑全量测试确认无回归（见下），但**真库路径的改动（`UPDATE asset ... motif_id` 与 trace 重排序）还没在真 PG 上执行过**，这一条要和 §5.1 一起补验。
