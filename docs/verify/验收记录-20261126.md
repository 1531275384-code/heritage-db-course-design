### 本机没有 Docker，pgvector 是怎么来的

`sql/00_compat_vector.sql` 里写过「pgvector 在 Windows 上没有官方预编译包，需要 MSVC 自己编」。
这次没有装 MSVC，而是用 portable 的 `micromamba` 从 conda-forge 取了一份**同一 ABI 的
MSVC 构建**，落在项目外（不进仓库）：

```bash
# 1) 取 micromamba（单文件，无需管理员权限）
curl -L -o mm.tar.bz2 https://micro.mamba.pm/api/micromamba/win-64/latest
tar -xjf mm.tar.bz2
# 2) 建环境：PostgreSQL 16 + pgvector
./Library/bin/micromamba.exe create -y -p C:/pgvec-runtime/env \
    -c conda-forge "postgresql=16" pgvector
# 3) 起库（端口 55433，与项目自带运行时 55432 错开）
./env/Library/bin/initdb.exe -D C:/pgvec-runtime/data -U postgres --encoding=UTF8 --locale=C --auth=trust
./env/Library/bin/postgres.exe -D C:/pgvec-runtime/data -p 55433 -c listen_addresses=127.0.0.1
```

两个本机坑（与本项目无关，但会让人误判成项目问题）：

1. **应用控制策略拦截 Temp 目录下的 DLL**：环境放在 `%TEMP%` 时 `CREATE EXTENSION pgcrypto`
   报 `An Application Control policy has blocked this file`。把运行时移出 Temp 即可。
2. `pgcrypto.dll` 仍被策略拦，改用项目自带运行时（EDB 16.4，同为 MSVC x64）的同名 DLL 覆盖后正常加载；
   `vector.dll` 本身不受影响。

> 官方推荐路径仍是 `docker compose up -d`（`pgvector/pgvector:pg16`）；
> 上面只是「没有 Docker 时如何得到等价环境」的可行替代，不改变项目的部署方式。

## 三、HNSW 实测证据

`check_pg.py` 第 10 节逐项核对，均通过：

```
✓ pgvector 扩展已安装  —— vector 0.8.6
✓ idx_public_motif_hnsw 存在且为 HNSW(base_vector)
✓ idx_feature_vector_hnsw 存在且为 HNSW(embedding)
✓ idx_public_motif_hnsw 可被近邻查询选中（enable_seqscan=off 验证）—— 3 行；默认计划=顺序扫描
✓ idx_feature_vector_hnsw 可被近邻查询选中（enable_seqscan=off 验证）—— 0 行（+ 事务内临时探针）；默认计划=命中索引
```

- `public_motif` 3 行时默认走顺序扫描——这是**正确选择**，不是失败；用 `enable_seqscan=off`
  证明索引确实可用，两种计划分别打印、不混用。
- `feature_vector` 新装库天然 0 行，原先只能记 GAP。现改为**事务内插一条探针向量 → EXPLAIN →
  回滚**，既不落数据，又能真实证明索引可被选中。

性能采集（`bench_20261126-193234.md`）：

| 场景 | 数据量 | 默认 | 关闭索引扫描 |
|---|---|---|---|
| `vector_knn` | 3 行 | 0.44 ms | 0.40 ms |
| `vector_knn_syn5000` | 5000 行（合成） | **0.76 ms（Index Scan using idx_public_motif_hnsw）** | 22.31 ms |
| `pending_audit` | 2 行 | 0.15 ms | 0.17 ms |
| `asset_ledger` | 8 行 | 0.40 ms | 0.44 ms |

5000 行时 HNSW 比顺序扫描快约 **29 倍**，且默认计划就命中索引——这才是「HNSW 生效」的证据。
合成数据在事务内生成、脚本结束整笔回滚，**不落库**；随机种子固定，换机器可复现。

## 五、已知边界

1. **`run_e2e_inline` 在真库模式下不能连续跑两遍**：第 4 步上传的样本文件与第 13 步的幂等用例是同一个文件，
   第二次运行时上传会命中 `duplicate_of`，拿到的是上一次已终审的资产（→ 409）。
   验证真库链路请先重建库，或只在演示模式重复跑。
2. **`bench_pg` 的规模结论来自合成向量**，只说明索引与计划行为，不代表真实纹样分布下的召回率。
3. 浏览器内核：`python -m playwright install chromium` 在本机网络下**卡在 CDN 十几分钟零字节**。
   已加 `tests/browser_launch.py` 兜底：自带内核 → 系统 `msedge` → 系统 `chrome`，
   可用 `ICH_BROWSER_CHANNEL` 强制指定。三套 UI 断言在本机用 Edge 跑通（49 / 52 / 58 项）。
4. 特征向量属**派生数据、可重建**；`ich_heritor` 拥有该表 `DELETE` 权限意味着理论上可删他人向量
   （降低检索质量，不影响权属与审核结论）。要按人隔离需引入 RLS + 每用户会话变量，超出当前设计范围。

## 六、本轮追加：谱系 DAG 约束 + 多会话并发实测

### 6.1 起因

对 `sql/02` 与 `app/services.py` 的复核提出三点疑问：

1. `asset_genealogy` 只有 `CHECK (parent <> child)` 与 `UNIQUE(parent, child)`，
   **没有阻止多跳成环的机制**；表注释写的是「由应用层做环检测」，但代码里没有任何环检测。
2. `v_asset_trace_chain` 是**时间维度**的事件流，不能回答"往上第 N 代是谁"；
   项目里没有任何 `WITH RECURSIVE`。
3. `approve_asset` 的 `FOR UPDATE` 与 `uq_lic_exclusive_active` 只是注释里的说法，
   没有真实多会话测试证明「两个专家同时终审」只会成功一个。

### 6.2 改动

| 位置 | 改动 |
|---|---|
| `sql/02` `B5` | 新增 `fn_genealogy_no_cycle()` + `trg_genealogy_no_cycle`（BEFORE INSERT OR UPDATE）：判据为「child 已是 parent 的祖先」，向上递归查祖先链；命中则 `RAISE EXCEPTION ... ERRCODE 23514` 并给出闭环路径 |
| 同上 | 触发器内取 **事务级咨询锁** `pg_advisory_xact_lock(hashtext('ich.asset_genealogy.dag'))`：两个会话同时插 A→B 与 B→A 时，行锁锁不住（两行互不相干），逐行检查会双双通过（写偏斜） |
| `sql/02` `C4` | 新增 `v_asset_lineage`：`WITH RECURSIVE` 展开任意深度祖先链，输出 `depth` / `path` / `is_direct_parent` / `relation_type`；递归带 `NOT (… = ANY(path))` 兜底与深度上限 64 |
| `sql/02` 权限段 | 三档角色对 `v_asset_lineage` 的 SELECT；顺带补上 `ich_admin` 对四个视图的 SELECT（`GRANT ... ON ALL TABLES` 不含视图，这是 PostgreSQL 的语义细节） |
| `scripts/gen_rules.py` | 新增触发器语义签名 `fn_genealogy_no_cycle` → `kind="dag"`（图结构判定，单行样本表达不了，不参与接受/拒绝对拍），规则表自动收录第 10 个触发器 |
| `tests/test_pg_concurrency.py`（新） | 30 项多会话验收，见 6.3 |
| `tests/check_pg.py` | 视图/触发器由「按个数核对」改为「按名字核对」（个数对得上但换了个对象，是漏检最严重的一种） |
| `tests/test_sql_structure.py` | 递归视图的 CTE 名不再被误判成"未定义表"；关键约束清单加入环检测触发器 |

### 6.3 并发验收怎么做的

不是"顺序调用两次"——那测不出并发。做法：

1. `CREATE DATABASE ... TEMPLATE ich_heritage` 克隆一个**一次性沙箱库**，
   所有写入落在沙箱，跑完 `DROP DATABASE`（追加式表不可删，直接在演示库跑会越跑越脏）。
2. 每个场景用 `threading.Barrier` 让两个线程同一瞬间发起，各自从连接池取独立连接。
3. 结论断言的是不变量而非"谁赢"。

| 场景 | 结果 |
|---|---|
| 双专家同时终审同一资产 | 恰好 1 个成功，另一个 409「已终审通过，禁止重复终审」；`audit_record` 只有 1 条 approved；`system_audit_log` 只有 1 条 UPDATE |
| 外部会话持 `FOR UPDATE` 时终审 | `pg_stat_activity` 观测到 `wait_event_type=Lock`（**串行化真的发生了**，不是第二个请求来晚了）；持锁方提交后终审成功 |
| 两份独占授权并发登记 | 恰好 1 份成功，另一份 409；生效独占记录 1 条（`uq_lic_exclusive_active`） |
| 三跳闭环 g4→g1 | 拒绝，报错含闭环路径 `15 → 14 → 13 → 12` |
| 菱形 DAG（g1→g3） | 允许（同一祖先多路径是合法血缘） |
| 自环 / 重复边 | 分别由 `ck_gen_not_self`（23514）与 `uq_gen_edge`（23505）拦下 |
| UPDATE 把 g1→g3 改成 g3→g1 | 拒绝（否则改一条边就能绕过环检测） |
| 两会话同时插 s1→s2 与 s2→s1 | 恰好 1 条落库，另一条判成环 |
| 递归祖先链 | g4 的祖先 4 条：depth `1/2/2/3`；g1 经两条路径出现；最深路径 `g4→g3→g2→g1`；根节点无祖先行 |
| 三档角色读 `v_asset_lineage` | `ich_heritor` / `ich_expert` / `ich_admin` 均可读（显式事务内 `SET LOCAL ROLE`，避免 autocommit 下测出假通过） |

### 6.4 咨询锁不是摆设：对照实验

把同一个环检测函数复制一份、**去掉 `pg_advisory_xact_lock`**，两个会话各插一条反向边（都先插入、都不提交，制造重叠窗口）：

```
去掉咨询锁: 结果=['ok', 'ok']        实际边数=2   ← 双双通过，库里真的成环
带咨询锁:   结果=['CheckViolation', 'ok']  实际边数=1
```

这解释了为什么"逐行检查"不够：并发写偏斜下，两个会话都看不到对方**未提交**的边。
实验后已删除临时函数，触发器恢复为 `fn_genealogy_no_cycle`。

### 6.6 仍然存在的边界（如实记录）

1. **谱系没有写入入口**：`asset_genealogy` 的 0 行不是"没人用"，而是**没有任何 API/服务在写它**；
   `ich_heritor` 也没有该表的 INSERT 权限。本轮只把"写得进去时必须合法"这条守住了，
   "谁来写"是产品决策（开放登记时还要决定"谁能给哪个资产建边"，否则可越权伪造血缘）。
2. 并发测试依赖**克隆模板库**：要求目标库当时没有其它活动连接；有 API 服务在跑时会明确失败并提示，
   不会去终止别人的会话。
3. 咨询锁把谱系写入串行化：写入是低频操作，代价可接受；若将来批量导入谱系，应改为按连通分量加锁。
