### 本机没有 Docker，pgvector 是怎么来的

`sql/00_compat_vector.sql` 里写过「pgvector 在 Windows 上没有官方预编译包，需要 MSVC 自己编」。
这次没有装 MSVC，而是用 portable 的 `micromamba` 从 conda-forge 取了一份**同一 ABI 的
MSVC 构建**，落在项目外（不进仓库）：

```bash
# 1) 取 micromamba（单文件，无需管理员权限）
curl -L -o mm.tar.bz2 https://micro.mamba.pm/api/micromamba/win-64/latest
tar -xjf mm.tar.bz2
# 2) 建环境：PostgreSQL 16 + pgvector
./Library/bin/micromamba.exe create -y -p C:/pgvec-runtime/env \
    -c conda-forge "postgresql=16" pgvector
# 3) 起库（端口 55433，与项目自带运行时 55432 错开）
./env/Library/bin/initdb.exe -D C:/pgvec-runtime/data -U postgres --encoding=UTF8 --locale=C --auth=trust
./env/Library/bin/postgres.exe -D C:/pgvec-runtime/data -p 55433 -c listen_addresses=127.0.0.1
```

两个本机坑（与本项目无关，但会让人误判成项目问题）：

1. **应用控制策略拦截 Temp 目录下的 DLL**：环境放在 `%TEMP%` 时 `CREATE EXTENSION pgcrypto`
   报 `An Application Control policy has blocked this file`。把运行时移出 Temp 即可。
2. `pgcrypto.dll` 仍被策略拦，改用项目自带运行时（EDB 16.4，同为 MSVC x64）的同名 DLL 覆盖后正常加载；
   `vector.dll` 本身不受影响。

> 官方推荐路径仍是 `docker compose up -d`（`pgvector/pgvector:pg16`）；
> 上面只是「没有 Docker 时如何得到等价环境」的可行替代，不改变项目的部署方式。

### 建库步骤（真库一次性）


## 三、HNSW 实测证据

`check_pg.py` 第 10 节逐项核对，均通过：

```
✓ pgvector 扩展已安装  —— vector 0.8.6
✓ idx_public_motif_hnsw 存在且为 HNSW(base_vector)
✓ idx_feature_vector_hnsw 存在且为 HNSW(embedding)
✓ idx_public_motif_hnsw 可被近邻查询选中（enable_seqscan=off 验证）—— 3 行；默认计划=顺序扫描
✓ idx_feature_vector_hnsw 可被近邻查询选中（enable_seqscan=off 验证）—— 0 行（+ 事务内临时探针）；默认计划=命中索引
```

- `public_motif` 3 行时默认走顺序扫描——这是**正确选择**，不是失败；用 `enable_seqscan=off`
  证明索引确实可用，两种计划分别打印、不混用。
- `feature_vector` 新装库天然 0 行，原先只能记 GAP。现改为**事务内插一条探针向量 → EXPLAIN →
  回滚**，既不落数据，又能真实证明索引可被选中。

性能采集（`bench_20261126-193234.md`）：

| 场景 | 数据量 | 默认 | 关闭索引扫描 |
|---|---|---|---|
| `vector_knn` | 3 行 | 0.44 ms | 0.40 ms |
| `vector_knn_syn5000` | 5000 行（合成） | **0.76 ms（Index Scan using idx_public_motif_hnsw）** | 22.31 ms |
| `pending_audit` | 2 行 | 0.15 ms | 0.17 ms |
| `asset_ledger` | 8 行 | 0.40 ms | 0.44 ms |

5000 行时 HNSW 比顺序扫描快约 **29 倍**，且默认计划就命中索引——这才是「HNSW 生效」的证据。
合成数据在事务内生成、脚本结束整笔回滚，**不落库**；随机种子固定，换机器可复现。

## 四、本轮修掉的问题

| # | 问题 | 性质 | 处理 |

| 1 | `sim/rules.py` 与 `sql/02` 指纹漂移 | 既有缺陷 | `python -m scripts.gen_rules` 重新生成；规则本体未变，仅指纹更新 |

| 8 | Playwright 自带内核下载卡死，三套 UI 断言跑不起来 | 环境健壮性 | 新增 `tests/browser_launch.py`：自带内核 → `msedge` → `chrome` 逐级兜底，`ICH_BROWSER_CHANNEL` 可强制指定 |

## 五、已知边界

1. **`run_e2e_inline` 在真库模式下不能连续跑两遍**：第 4 步上传的样本文件与第 13 步的幂等用例是同一个文件，
   第二次运行时上传会命中 `duplicate_of`，拿到的是上一次已终审的资产（→ 409）。
   验证真库链路请先重建库，或只在演示模式重复跑。
2. **`bench_pg` 的规模结论来自合成向量**，只说明索引与计划行为，不代表真实纹样分布下的召回率。
3. 浏览器内核：`python -m playwright install chromium` 在本机网络下**卡在 CDN 十几分钟零字节**。
   已加 `tests/browser_launch.py` 兜底：自带内核 → 系统 `msedge` → 系统 `chrome`，
   可用 `ICH_BROWSER_CHANNEL` 强制指定。三套 UI 断言在本机用 Edge 跑通（49 / 52 / 58 项）。
4. 特征向量属**派生数据、可重建**；`ich_heritor` 拥有该表 `DELETE` 权限意味着理论上可删他人向量
   （降低检索质量，不影响权属与审核结论）。要按人隔离需引入 RLS + 每用户会话变量，超出当前设计范围。
