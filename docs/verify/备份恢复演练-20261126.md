# 备份恢复演练报告

- 演练时间：2026-11-26 23:33
- 源库：`ich_heritage`（PostgreSQL 16.15，pgvector 0.8.6）
- 恢复目标：临时库 `ich_restore_*`（`CREATE DATABASE ... TEMPLATE template0`，演练后 DROP）
- 脚本：`tests/test_backup_restore.py`
- 证据：`docs/verify/backup_restore_20261126-233346.json`（37 条断言逐条留证）
- 结果：**37 项通过 / 0 项失败，总耗时 11.6 秒**

> 这不是"写了备份方案"，而是"真的 dump 过一次、恢复到新库、逐对象比对、
> 并在恢复库上把终审事务正常跑通、再故意打断一次看成不成全回滚"。

| 项 | 值 |
|---|---|
| 命令 | `pg_dump -Fc -Z6 -f ich_heritage.dump` |
| 格式 | custom（文件头 `PGDMP`，可 `pg_restore -l` 选择性恢复） |
| 体积 | 96 404 字节（约 94 KiB） |
| 耗时 | 0.82 s |

| 退出码 | 0（stderr 空） |

体积小是因为当前库只有 111 行业务数据。按《物理存储与 TOAST 实测》的摊销
（约 7.5 KiB/条资产，其中 5.4 KiB 是向量与 HNSW），10 万条资产时 dump 量级在
700 MiB 上下 —— 备份窗口和存储规划要按这个量级算，不能按 94 KiB 估。

## 2. 恢复

| 项 | 值 |
|---|---|
| 命令 | `pg_restore -d ich_restore_xxx` |
| 耗时 | 1.49 s |
| 退出码 | 0 |

| 对象 | 数量 | 结果 |

| 索引（含 HNSW） | 26 | `pg_get_indexdef` 逐条一致 |
| 触发器 | 10 | `pg_get_triggerdef` 逐条一致 |
| 函数（项目自有，排除扩展成员） | 11 | `pg_get_functiondef` md5 一致 |
| 枚举类型及取值 | 3 | 标签与顺序一致 |
| 序列 | 8 | `last_value` / `is_called` 一致 |
| 表级授权 | 12 | `relacl` 一致 |
| **列级授权** | **532 条** | 逐条一致 |
| 数据行数 | 111 行 | 12 张表逐表一致 |
| 内容指纹 | 12 表 | `md5(string_agg(row::text ORDER BY row::text))` 全等 |

其中三项是"恢复最容易丢、丢了最致命"的：**触发器**（丢了审计留痕就没了）、
**列级 GRANT**（丢了权限模型就塌了）、**序列当前值**（丢了第一条 INSERT 就撞主键）。
这三项都单独断言，没有混在"结构一致"一个勾里。

## 4. 一处真实差异，以及怎么判定它不是问题

6 条 CHECK 约束在恢复后**定义文本不同**：

```
源库：  CHECK (((state)::text = ANY ((ARRAY['pending'::character varying, ...])::text[])))
恢复库：CHECK ((((state)::text = ANY (ARRAY[('pending'::character varying)::text, ...]))))
```

原因：`pg_dump` 会把"整数组转 `::text[]`"改写成"逐元素转 `::text`"。两者语义相同，
但 `pg_get_constraintdef` 的输出不同 —— 如果直接拿文本比对，这 6 条会被误判为
"备份丢了约束"。

处理方式（两步，缺一不可）：

1. **归一化比对**：去掉显式类型转换（含数组形式的 `::text[]`）、括号、空白后比较，
   6 条全部相等；同时仍比对约束名、类型（`c`/`f`/`u`/`p`）、所属表、`convalidated`。
2. **行为证据**：在两个库上分别插入非法枚举值，都必须返回 `22P02`。
   实测 `{"源库": "22P02", "恢复库": "22P02"}` —— 限制仍在，不是"文本对齐了但约束没生效"。

这一条没有被我"抹平"，它写在报告里，因为**下次换 PostgreSQL 大版本时这个差异还会出现**。

## 5. 权限实测：不只看 ACL 文本，看它是否还有选择性

ACL 文本一致 ≠ 权限仍然正确（比如恢复时图省事把角色加成 superuser）。所以在恢复库上
以 `ich_heritor` 身份实跑了三条语句：

| 操作 | 预期 | 实测 |
|---|---|---|
| `UPDATE asset SET title=title` | 允许（列级授权内的列） | 成功，rowcount=1 |
| `UPDATE asset SET right_level='public'` | 拒绝（列级授权**排除**该列） | `42501` |
| `UPDATE system_audit_log SET ...` | 拒绝（追加式表已 REVOKE） | `42501` |

第一条通过最关键：它证明拒绝来自**列级选择性**，而不是"整张表都没权限"这种把功能
一起恢复坏掉的情况。

补充断言：三个业务角色 `ich_heritor / ich_expert / ich_admin` 均存在，
`rolsuper = false`、`rolcanlogin = false` —— 防止"恢复时给了超级用户"这种隐性降级。

## 6. 功能烟测：恢复库能不能干活

### 6.1 HNSW 检索

往恢复库写入 3 条临时归一化向量，用第 2 条做查询向量：

- 期望最近邻 `1002`，实得 `1002`；
- 事务回滚后残留 `0` 条。

说明恢复出来的 HNSW 索引不仅能创建，而且**能正确返回结果**，不只是"目录里有这个索引"。

### 6.2 递归谱系视图

`v_asset_lineage` 在恢复库可正常查询（定义 md5 已比对一致，此处是执行层验证）。

### 6.3 终审正常提交（三表联动）

对 `asset_id=1003` 调用真实的 `app.services.approve_asset()`：

| 表 | 事件前 | 事件后 |
|---|---|---|
| `asset` | `public / pending / v1 / updated_at=2026-11-22 20:37` | `derived / approved / v2 / updated_at=2026-11-26 23:33` |
| `audit_record`（id=5） | `pending`，expert_id=NULL | `approved`，expert_id=2，decided_at=23:33:45 |
| `system_audit_log` | 该资产 1 条 | 2 条（触发器新写入 1 条） |

三张表在同一事务里一起变，`version_no` 由 `trg_asset_touch` 自增 1，符合设计。

### 6.4 注入异常 → 三表全回滚（本轮重点）

做法：包住 `services.open_tx`，让事务进行到"两条 UPDATE 已发出、只剩最后一条回读"时抛
`RuntimeError`。这模拟的是"应用在提交前崩了"，比手工 `BEGIN; ROLLBACK;` 更接近真实事故。
（`asset` 的 AFTER 触发器此时已在事务内执行过；它写的日志是否真的随回滚消失，
由下面的 `system_audit_log` 条数来判定，不靠推断。）

对 `asset_id=1006` 的结果：

| 表/字段 | 异常前 | 异常后 | 判定 |
|---|---|---|---|
| `asset.right_level` | public | public | 未变 |
| `asset.audit_status` | pending | pending | 未变 |
| `asset.version_no` | 1 | 1 | 未变 |
| `asset.updated_at` | 2026-11-24 20:37:22.980277 | 同一值（微秒级一致） | 未变 |
| `audit_record`（id=12） | `pending / expert_id=NULL / decided_at=NULL` | 完全同上 | 未变 |
| `system_audit_log` 条数 | 1 | 1 | 未变 |

异常确实在事务中途抛出（`RuntimeError: fault injection: ...`），而三张表**一条痕迹都没留**。
这就是"要么同时成功、要么整体消失"的实测证据 —— 不是靠读代码推断的。

### 6.5 绕过应用直连改状态

以 `ich_expert` 身份直接 `UPDATE asset SET audit_status='approved'`（不经 `approve_asset`）：

```
ERROR: 终审结论必须由 approve_asset()/reject_asset() 写入（pending → approved）  (42501)
```

数据库闸门在恢复库里依然生效。第一版探针挑了一条已终审的资产，写同值是幂等操作、
不会被拦 —— 那是我测试设计的问题，已改为挑 `pending` 资产。

## 7. 源库未被污染

演练期间对 `1003` / `1006` 的所有写入都发生在临时库。演练结束后核对源库：

```
1003 | public | pending | 1
1006 | public | pending | 1
```

与演练前完全一致；`pg_database` 中也只剩 `ich_heritage / postgres / template0 / template1`，
临时库已清理（`DROP DATABASE ... WITH (FORCE)`）。

## 8. 局限（必须一起读）

1. **同集群恢复**。角色（`ich_heritor` 等）是集群级对象，本次恢复没验证"跨集群缺角色"的场景。
   真实异地恢复要先建角色再 restore，否则 GRANT 会报 role does not exist。
2. **未做 PITR**。本演练验证的是逻辑备份（`pg_dump`），不含 WAL 归档 / 时间点恢复。
   误删数据要回到"删除前一秒"，逻辑备份做不到，需要 `archive_mode` + basebackup。
3. **未验证跨大版本恢复**。同版本 16.15 内恢复。跨大版本需重装扩展并 `REFRESH`，
   CHECK 的 deparse 差异也会更多。
4. **未做加密与异地**。dump 文件是明文，落在本机临时目录；生产应加密后传异地并校验 SHA-256。
5. **数据量小**。111 行、94 KiB 的恢复只证明了"全流程通"，没证明"大库能在窗口内恢复完"。
   容量规划参考物理存储报告的外推值。

## 9. 复现

```bash
export PG_DSN="host=127.0.0.1 port=55433 user=postgres dbname=ich_heritage"

python -m tests.test_backup_restore            # 完整演练，退出码 0 = 全过
python -m tests.test_backup_restore --keep     # 保留临时库与 dump，便于排查
```

前置：`pg_dump` / `pg_restore` 在 `PG_BIN` 或 PATH 中（本机用项目自带
`_env/pgsql/bin`），且源库当前无其他连接（克隆/恢复期间要求）。
输出同时写入 `docs/verify/backup_restore_<时间戳>.json`。
