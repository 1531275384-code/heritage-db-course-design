# 物理存储与 TOAST 实测报告

- 环境：PostgreSQL 16.15 (Windows x64)，pgvector 0.8.6，`shared_buffers=128MB`，本机 SSD
- 被测表：`asset`、`feature_vector`（1:1 垂直拆分）
- 数据规模：20008 条资产 / 20000 条 512 维向量（沙箱库克隆后造数，测完即 DROP，未污染演示库）
- 生成脚本：`scripts/bench_storage.py`
- 机器输出：`docs/verify/storage_20261126-232920.md`（同目录 `.json` 为原始数值）
- 实测时间：2026-11-26 23:29

> 本报告的数字全部由脚本在真实 PostgreSQL 上跑出，不是估算。凡是无法在本机严谨测量的
> （例如真正的冷缓存读），文中直接写"未测"，不给推测值。

---

## 1. 为什么值得测这件事

`sql/01_init.sql` 把 512 维向量拆到 `feature_vector` 旁边，注释写的是
"避免读取资产主表时总要处理 512 维向量"。这句话对不对，取决于三个可测的量：

1. 向量在磁盘上究竟占多少（含 TOAST 与索引）；
2. 不读向量时，主表是不是真的"轻"；
3. 读向量时，代价是不是真的能靠索引摊掉。

以下逐条给数。

---

## 2. 表与 TOAST 占用

| 对象 | 堆 | TOAST 堆 | TOAST 索引 | 普通索引 | 合计 | 每行 |
|---|---|---|---|---|---|---|
| `asset` | 6.5 MiB | 26.0 MiB | 312 KiB | 3.2 MiB | 36.1 MiB | 1.8 KiB |
| `feature_vector` | 2.0 MiB | 52.1 MiB | 896 KiB | 52.5 MiB | 107.6 MiB | 5.5 KiB |

两处必须点明的细节：

- **`feature_vector` 的堆只有 2.0 MiB / 20000 行 ≈ 105 B/行**。这 105 B 装的是
  `fv_id + asset_id + model_name + model_version + created_at + 18 B 的 TOAST 指针`，
  **不含 2048 B 的向量本体**。也就是说：向量确实不在主堆里，`storage = external`
  在物理上生效了。
- **TOAST 表实际 40000 行，正好是 20000 的 2 倍**。2052 B 的向量超过单个 chunk 的
  容纳上限（约 1996 B），每行被切成 2 个 chunk 存。这是查 `pg_toast.pg_toast_<oid>`
  的真实行数得到的，不是按阈值推算的。

`asset` 侧：堆 6.5 MiB（341.6 B/行），TOAST 26.0 MiB（1.38 KiB/行）。TOAST 里 13334 行，
来自 6667 条"超长描述"样本 × 2 chunk —— 与向量同样的切分行为。

---

## 3. 512 维向量到底占多少

| 口径 | 字节/行 | 说明 |
|---|---|---|
| 裸数据（512 × float4） | 2048 | 理论下限 |
| `pg_column_size(embedding)` | 2052 | 多 4 B 的类型头 |
| TOAST 实际占用 | 2778.7 | 含 2 个 chunk 的头 + 指针 |
| HNSW 索引 | 2754.6 | `m=16, ef_construction=64` |
| 堆内那一行 | 105.3 | 只有指针与元数据 |

结论很直白：**一条向量在磁盘上要 5.4 KiB，其中向量本体只占 2.0 KiB，索引占 2.7 KiB**。
HNSW 索引的体积是向量本体本身的 1.34 倍、是所在堆的 26 倍。索引不是"附赠的小开销"，
它是这条记录最主要的空间成本。

按此摊销，2 万条资产需要约 144 MiB；线性外推到 10 万条约 700 MiB，其中约 260 MiB 是 HNSW。
这个数字对备份/迁移是硬约束（见《备份恢复演练》报告：dump 体积同样由向量主导）。

## 4. description 的压缩与 TOAST 阈值

造数时按三种画像各 1/3 行，用来观察 pglz 压缩与 2 KiB 行外阈值：

| 画像 | 原始字节 | 存储字节 | 压缩率 | 是否行外 |
|---|---|---|---|---|
| P1 短描述（约 50 字） | 115 | 116 | 100.9% | 否 |
| P2 长描述（约 800 字中文，重复句式） | 2584 | 186 | **7.2%** | 否（压完就装得下） |
| P3 超长（3840 B 高熵十六进制） | 3844 | 3844 | 100.0% | **是（2 chunk）** |

这里有个容易误判的点：**`pg_column_size(t.*)` 会把行外列解压后计入**。
本次抽样的 P3 行输出 4072 B，看上去像"这行在磁盘上占 4 KB"，实际它的堆内记录只有
约 341 B，3844 B 在 TOAST 里。所以判断磁盘占用只能看 `pg_relation_size` /
`pg_total_relation_size`，不能看 `pg_column_size(row)`。第一版报告曾在这里写错，已修正。

另一条经验：真实中文长描述（P2）压缩到 7.2%，通常**进不了 TOAST**；只有高熵或
图像/JSON 这类压不动的长文本才会真正行外。所以"给 description 加 TOAST"不是必然发生的事，
取决于内容。

## 5. 读取成本：拆表省的是读放大

同一份数据、同一条列表查询（按 `owner_id` 走 `idx_asset_owner_time` 取最近 20 条）：

| 场景 | 顶层命中页 | 读盘页 | 耗时 |
|---|---|---|---|
| 只取展示列 | **5** | 2 | 0.083 ms |
| 多带 `description` | 4 | 0 | 0.052 ms |
| 同样 20 行，连带 `embedding` | **182** | 79 | 5.808 ms |

读 20 行的展示数据只要 5 个页；一旦要连带向量，要 182 个页 —— **36.4 倍**，耗时 70 倍。
这 177 个额外页不是"数据变多"，而是每行都要多跳一次 TOAST 链（toast 索引页 + 2 个 chunk 页）。

这正是拆表的意义：**不是让总空间变少**（总量一样），**而是让不关心向量的查询
不必为向量付页数**。如果向量和资产同表，上面第一行的 5 页会退化成"每页只装 3~4 行"，
列表页的缓存命中率会整体下移。

一个反例也一并记录：直接写 `asset JOIN feature_vector ... ORDER BY created_at LIMIT 20`
（不先限行），规划器会选"全表 Hash Join + top-N 排序"，实测 1091 页 / 22.9 ms。
这说明**拆表不等于自动变快**，写法上要先限行再取向量，否则拆表的收益会被糟糕的计划吃掉。

## 6. HNSW 的收益与代价

| 场景 | 页数 | 耗时 |
|---|---|---|
| HNSW top-5 | 1 353 | 3.05 ms |
| 顺序扫描基线（`enable_indexscan=off`） | 117 450 | 209.74 ms |

- 页数比 **86.8×**，时间比 **68.7×**。
- HNSW 的 1353 页里，绝大部分是索引自身的图结构页（52.1 MiB ≈ 6669 页），
  命中率高时这部分常驻 shared_buffers；顺序扫描则必须把 117k 页全部过一遍。

代价就是第 3 节那 2.7 KiB/行。对"读多写少、检索频繁"的纹样查重场景，这笔交易是划算的；
对"只存不查"的归档场景则不划算 —— 这也是索引可以和表分开建、按需开关的原因。

## 7. 方法与局限（必须一起读）

**做了什么**

- 用 `CREATE DATABASE ... TEMPLATE` 克隆一次性沙箱库，在里面造 2 万行真实结构的数据，
  测完 `DROP DATABASE ... WITH (FORCE)`；演示库 `ich_heritage` 的数据没有被改动。
- 所有尺寸取自 `pg_relation_size` / `pg_total_relation_size` / `pg_indexes_size`，
  TOAST 行数取自 `SELECT count(*) FROM pg_toast.pg_toast_<oid>`。
- 读取成本取自 `EXPLAIN (ANALYZE, BUFFERS)` 的顶层 `Buffers` 行。

**没做什么 / 不能声称什么**

- **没有测冷缓存**。Windows 没有 `drop_caches`，重启实例也清不掉 OS 文件缓存。
  因此本报告以 shared buffers 页数为主指标（由页数决定，与缓存状态无关），
  耗时只作同机参考，不跨机器比较。
- `shared read` 一列在部分场景非零，是首次访问的真实磁盘读；但因为无法保证每次都冷，
  报告结论一律不建立在读盘页上，只用命中页。
- 数据是合成的（标题、描述、向量分布），行宽分布比真实业务更极端（刻意放入高熵长文本）。
  它回答的是"物理机制如何运作"，不是"你们的库会有多大"。

## 8. 复现

```bash
# 先确保库已按 sql/01→03 建好，且没有别的会话连着它（克隆模板库的要求）
export PG_DSN="host=127.0.0.1 port=55433 user=postgres dbname=ich_heritage"

python -m scripts.bench_storage            # 默认 2 万行
python -m scripts.bench_storage --rows 50000
python -m scripts.bench_storage --keep     # 保留沙箱库以便手工排查
```

脚本退出码 0 表示测量完成；输出同时写入 `docs/verify/storage_<时间戳>.{md,json}`。
