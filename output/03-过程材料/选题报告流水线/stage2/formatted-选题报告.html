报告摘要

本报告提出并论证一个"非遗数字资产分级确权与溯源"系统的选题。现实问题是非遗数字化过程中出现的权属真空：公有母题被私人圈占、改编幅度无从量化、权属结论不可追溯、授权流转缺少存证。本项目的技术切入点是把权属分级问题转化为向量空间中的距离判定问题——用图像特征向量的余弦相似度作为"借鉴程度"的客观代理指标，用 PostgreSQL 的约束、触发器、视图、事务与列级权限体系保证判断过程的规范性。

项目已交付一个可运行系统，含 8 张业务表、3 个视图、7 个触发器、14 个索引、4 个数据库角色、18 个 HTTP 端点、三档特征提取后端，共约 9843 行代码；192 项自动化测试全部通过，并有 8 张真实浏览器全流程截图。本报告如实声明了最大验证缺口——SQL 脚本未在真实 PostgreSQL 上执行——并说明替代验证措施及 4 个主动发现并修复的缺陷。

关键词：非遗数字化；权属分级；向量检索；pgvector；触发器审计；列级权限；事务原子性

一、选题背景

本章先交代现实问题，再说明技术切入点，最后界定本选题在“工具开发”与“规则约束”之间的定位。

（一）现实问题：非遗数字化的"确权真空"

非物质文化遗产的数字化正在快速推进——纹样、绣片、器型被拍摄、扫描、矢量化后进入机构数据库与文创供应链。但数字化本身没有解决权属问题，反而制造了一个新的真空地带。其具体表现可以归纳为四条：

表 1-1　非遗数字化中的四类权属问题
问题具体表现
公有母题被独占蝴蝶纹、缠枝莲纹、回纹这类流传数百年的传统纹样属公有领域，但某人把纹样稍作修饰后作为"原创作品"登记版权，进而向其他从业者主张权利，形成"传统资源的私人圈占"

权属结论不可追溯一个"原创"结论是怎么产生的、谁定的、依据什么，往往只存在于纸质档案或某个人的记忆里。一旦发生纠纷，举证困难

这些问题的共同根源是：权属判断是主观的、过程是断裂的、证据是不可验证的。

（二）技术切入点：图像相似度可以成为分级依据

非遗纹样的数字资产绝大多数是二维图像。这类图像具有一个对技术非常友好的特点：母题的结构特征高度稳定。

蝴蝶纹的对称双翼结构、缠枝莲纹的连续曲线缠绕关系、回纹的直角折线周期——这些不是创作者可以随意改变的东西，一旦改变就不成其为该纹样。因此"与既知公有母题的特征距离"可以作为"借鉴程度"的客观代理指标。

这意味着一件事：把权属分级问题转化为向量空间中的距离判定问题。现代计算机视觉技术（CLIP、ResNet）可以把图像映射到 512 维语义空间，用余弦相似度度量"像不像"；PostgreSQL 的 pgvector 扩展提供了 HNSW 近似最近邻索引，能在毫秒级完成百万级向量的检索。

但这里有一个必须守住的边界——相似度只能作为建议，不能作为判决。这是本项目的核心设计立场，第三章将详细展开四层防护机制。

（三）选题定位

本项目不追求"用 AI 自动定权属"。恰恰相反，它要回答的是另一个问题：当 AI 已经能给出相当可靠的权属判断时，如何从工程上保证它不越界？

这个问题比"怎么做相似度检索"更贴近数据库课程的核心——它涉及列级权限、事务原子性、触发器审计、视图抽象、并发控制。因此本选题是一个以数据库原理为主干、AI 作为业务驱动的综合设计题，而非一个 AI 调参题。

2. 为什么 feature_vector 要垂直拆分

这是一个值得单独讨论的设计决策。把 512 维向量直接放 asset 表也完全可行，但拆开的理由是访问模式差异：

  • asset 表被高频读（列表、详情、统计），但几乎从不读向量列
  • 向量列有 512 个 NUMERIC，单行体积大，全表扫描时会显著放大 I/O
  • 向量只在 analyze 时写入一次，之后只读

1:1 垂直拆分让"表变窄、行变小"，主表扫描更快。这是典型的用范式换性能的取舍——严格说拆分后仍是 3NF，但拆分的动机不是范式要求而是物理设计。代价是关联查询多一次 JOIN，这个代价在高频路径上可以忽略（因为高频路径根本不查向量）。

3. 索引设计：每个索引都对应一条真实查询

项目共 14 个索引，没有一个是"感觉可能有用"加的。以下三个有代表性：

部分索引（Partial Index）

CREATE INDEX idx_asset_pending ON asset (created_at DESC)

WHERE audit_status = 'pending';

专家工作台只查待审资产。待审资产在全表中永远是少数（终审后即离开该状态），全表索引会浪费大量空间在已终审行上。部分索引只索引"当前待审"的行，索引体积小一个数量级，命中更快。

HNSW 向量索引

CREATE INDEX idx_public_motif_hnsw ON public_motif

USING hnsw (base_vector vector_cosine_ops)

WITH (m = 16, ef_construction = 64);

m=16 控制图的连通度（每层最大连接数），ef_construction=64 控制建图时的候选队列大小。两者都在"召回率 vs 构建时间／内存"之间取平衡。vector_cosine_ops 使索引与 <=> 余弦距离运算符匹配，这样 ORDER BY base_vector <=> query 才能走索引。

这里有一个必须说清的坑：表只有 3 行时，查询规划器会认为顺序扫描比走 HNSW 更便宜，于是索引被忽略。所以项目在检索前显式 SET LOCAL enable_seqscan = off 强制走索引，目的不是提速（3 行数据提速无意义），而是让 EXPLAIN 能看到 Index Scan using ..._hnsw 这一证据。这个设置在文档中明确标注为"演示期措施，生产环境应去掉"。

部分唯一索引（保证业务唯一性）

CREATE UNIQUE INDEX uq_license_exclusive ON license_record (asset_id, licensee_id)

WHERE status = 'active';

业务规则是"同一资产对同一被授权方的有效独占授权只能有一条"，但历史上失效的授权记录允许多条（用于留档）。这种"在子集上唯一"的需求，普通 UNIQUE 约束表达不了，必须用部分唯一索引。

trg_asset_right_change 的实现值得展开。它不是简单地无条件记录每次 UPDATE，而是逐列用 IS DISTINCT FROM 比对，收集真正变化的列名：

IF NEW.right_level IS DISTINCT FROM OLD.right_level THEN v_changed := v_changed || 'right_level'; END IF;

IF NEW.audit_status IS DISTINCT FROM OLD.audit_status THEN v_changed := v_changed || 'audit_status'; END IF;

IF NEW.motif_id IS DISTINCT FROM OLD.motif_id THEN v_changed := v_changed || 'motif_id'; END IF;

IF NEW.owner_id IS DISTINCT FROM OLD.owner_id THEN v_changed := v_changed || 'owner_id'; END IF;

 

IF array_length(v_changed, 1) IS NULL THEN

RETURN NEW; -- 只改了标题/描述这类元数据，不写业务审计日志

END IF;

用 IS DISTINCT FROM 而非 <> 的原因：如果某列是 NULL，NULL <> NULL 结果为 NULL（既不是真也不是假），条件判断会漏掉。IS DISTINCT FROM 把 NULL 当普通值比较，语义正确。

"只对权属类字段留痕"这个过滤同样重要——否则用户每改一次标题描述都会产生一条审计日志，日志被噪音淹没，真正的权属变更反而找不出来。

v_asset_ledger 里有一个字段值得注意：

这一列直接输出"AI 建议与专家结论是否一致"，监管方可据此统计 AI 与专家的一致率。项目截图中台账页的"AI 与专家一致率"卡片就是基于这一列聚合出来的。这个设计让"AI 是否可信"变成可量化的运营指标，而不是一个说法。

6. 权限：数据库层 GRANT，而非应用层 if

这是全项目设计上最硬的一环。三个角色加一个服务账号：

ich_app 应用服务账号，后端以它连接数据库（表的 owner）

ich_heritor 传承人：只能看自己的资产，能上传、能申请审核

ich_expert 专家：可读全部资产，可写审核流水，★只有它能改 right_level

ich_admin 监管方：全量只读 + 可管母题库

关键的两条 GRANT：

-- 传承人可更新的列，★明确不含 right_level

GRANT UPDATE (title, description, file_path, file_hash, file_size, mime_type,

audit_status, ai_suggest_level, ai_confidence, ai_model_version, motif_id)

ON asset TO ich_heritor;

 

-- 只有专家能改权属结论

GRANT UPDATE (audit_status, right_level, motif_id) ON asset TO ich_expert;

注意这是列级 GRANT，不是表级。PostgreSQL 的列级权限让"传承人能改标题但不能改权属"这件事由数据库自己执行。

运行时机制是：后端统一用 ich_app 建连接池，每个请求在事务内 SET LOCAL ROLE ich_heritor（或 expert/admin）。SET LOCAL 的作用域仅限当前事务，事务结束自动复位，所以连接池中的连接归还后不会带着上一个用户的角色——这是一个容易踩的坑，用错 SET ROLE 会导致角色泄漏到后续请求。

（二）AI 模块：特征提取与分级建议

AI 模块只做两件事：把图像变成向量，把向量距离变成分级建议。前者要解决"环境依赖不确定"的问题，后者要解决"数字如何翻译成人能看懂的理由"的问题。

1. 三档特征后端与自动降级

统一 512 维不是巧合：ViT-B/32 的 projection dim 正好是 512，与数据库 VECTOR(512) 天然对齐，无需降维（降维会损失信息）。三个后端产出同维度向量，意味着换后端不需要改表结构，只需接受"历史向量与新向量不可直接比较"——这也是为什么 model_version 必须与向量一起落库。

[0:192) HOG-lite 方向梯度直方图（6×6 网格 × 8 方向）

[192:384) HSV 色度直方图（4×4 空间块 × H4×S4）

→ 只取色相/饱和度，对曝光差异鲁棒：苗绣靛蓝、青花钴蓝

[384:512) 多尺度 Laplacian 纹理能量（8 个尺度）

→ 捕捉疏密程度：细密苗绣 vs 简洁回纹

三段加权拼接的权重 0.51 / 0.23 / 0.26 不是拍脑袋定的，而是由 tests/tune_weights.py 做网格搜索标定，目标函数是同时满足"翻拍稳定性 ≥ 0.90"（同一作品不同拍摄应判为同一件）与"改编相似度 < 0.92"（改编作品不应被判为公有母题）这两个约束。这个脚本保留在仓库里，标定过程可复现。

2. 分级器：把相似度翻译成建议

app/ai/classifier.py 是一个纯函数模块，输入 SimilarityHit 列表，输出 Suggestion 数据类。分级规则如下（设 s 为与最相似公有母题的余弦相似度）：

表 3-5　四档分级规则
区间条件建议级别依据
s ≥ 0.92public 公有母题与传统母题高度重合，属公有领域，不得个人独占
0.80 ≤ s < 0.92 且 ≥2 个母题落入该区间derived 改编衍生与多个公有母题有实质重合，享有演绎著作权但须标注血缘
0.80 ≤ s < 0.92 但仅 1 个母题derived（置信度 ×0.9）存在明显借鉴但不构成整体复制
s < 0.80original 原创作品未发现与现存公有母题的实质重合

另有一条前置检查：若与已有私有资产相似度 ≥ 0.95，说明可能是抄袭他人作品，此时标记 flagged_as='duplicate'，不参与常规分级，直接交由专家人工核查。

置信度 conf 的构造值得一提——它不是硬编码常数，而是两个因子的乘积：

margin = 到最近阈值的距离（越远越自信）

separation = top1 与 top2 相似度的差（越大说明越不被并列候选干扰）

conf = squash(margin × 8.0) × squash(separation × 6.0 + 0.35)

这个设计的意义是：当一张图恰好压在 0.92 边界上，或 top1 和 top2 母题相似度几乎相同时，置信度会自动降低，提示专家"这个结论要仔细看"。相反，一张明显不相似的图会得到高置信度。置信度在这里不是一个装饰性的百分比，而是"该不该相信 AI"的信号。

3. 关键约束：分级器不 import 数据库模块

classifier.py 的 import 清单只有 dataclasses、app.config。它不 import app.db、不 import app.services。

这不是随手写的整洁代码，而是刻意为之的架构约束：从模块依赖图上就断绝了"分级器顺手改一下权属"的可能。一个模块如果没有数据库连接对象，它在物理上就写不了数据。这条约束由 tests/test_invariants.py 静态扫描保证——如果哪天有人给它加了 from app.db import ...，测试立刻失败。

（三）后端服务层

服务层是"业务规则与事务边界"的唯一归属地。下面先看分层，再看其中最关键的一个函数。

1. 分层与职责边界

app/api.py 路由层：只做 HTTP 编解码、鉴权、调服务层。不写业务 SQL

app/services.py 服务层：全部业务 SQL 与事务边界都在这里

app/db.py 基础设施：连接池 + open_tx 统一事务上下文

app/auth.py 鉴权：HS256 JWT（纯标准库实现）

app/schemas.py Pydantic 请求/响应模型

app/demo.py 演示模式：内存版同名同签名函数

共 18 个 HTTP 端点（7 个是需求指定的业务 API，其余为登录、健康检查、母题列表、授权查询等配套接口）。

2. 终审事务：全系统最关键的 60 行

services.approve_asset() 是全系统唯一写 asset.right_level 的函数。它必须在单个事务内完成 6 步：

表 3-6　终审事务的六个步骤
步骤动作校验
1SELECT ... FOR UPDATE OF a锁住资产行
2状态机校验（只有 pending 可终审）已 approved → 409
3SELECT ... FOR UPDATE 取待审流水同锁，避免双写
4UPDATE audit_record（专家结论）校验 rowcount == 1
5UPDATE asset（right_level + status）触发器在此写审计日志
6回读 system_audit_log作为触发器生效的证据

任一失败整体回滚。并发场景推演（两个专家同时点"通过"）：

T1: BEGIN → SELECT FOR UPDATE （拿到行锁）

T2: BEGIN → SELECT FOR UPDATE （阻塞等待）

T1: UPDATE audit_record / UPDATE asset → COMMIT（释放锁）

T2: 拿到锁，读到 audit_status 已是 'approved'

→ 命中状态机校验 → 抛 409 → ROLLBACK

结论：不会出现"同一资产被终审两次"，也不会出现"两条终审流水指向同一结论"。这一行为由 e2e 场景 8「并发／幂等保护：重复终审被拒」实测验证。

为什么用悲观锁而不是乐观锁（比对 version_no）：终审是低频、高价值、人工触发的操作，锁等待成本可忽略（阻塞 100ms 后自然成功）；乐观锁失败后要用户重试，体验差。version_no 仍然保留自增，用途是台账展示"该记录被改过几次"，而不是并发控制。

事务与触发器的关系是这个设计中最精妙的地方：UPDATE asset 会触发 trg_asset_right_change 写 system_audit_log。因为触发器运行在同一事务内，所以事务 COMMIT 时业务数据与审计日志一起生效，事务 ROLLBACK 时一起消失。这恰好满足"要么同时成功要么回滚"的要求：不会出现"日志说有变更但数据没变"。如果审计日志是由应用代码在事务外写，就必然存在这个不一致窗口。

analyze_asset() 则相反，它明确不写 right_level，只写 audit_record(state='pending') 与 asset.ai_suggest_level。这两个函数的行为差异由不变量测试强制检查。

3. 向量检索的双模式适配

app/ai/similarity.py 需要同时工作在两种数据库形态下（见本节第五点兼容层）。核心设计是只维护一份 SQL：

def cast_vec(expr: str = "%(q)s") -> str:

return f"{expr}::vector" if is_native() else f"ich_to_vector({expr})"

SQL 里用 f-string 注入 cast_vec() 的结果，两种模式的查询逻辑字面完全一致，只有参数绑定的写法不同。

为什么不用两份 SQL？因为两份 SQL 长期必然漂移——今天改了原生版的一个 WHERE 条件，三个月后没人记得降级版也有同样的问题。这才是真正的隐患。用一行函数做适配，代价极小，收益是"永远只有一个事实来源"。

同时 _apply_vector_settings() 在降级模式跳过 hnsw.ef_search 等设置——不是疏忽，是必须：降级模式没有 HNSW，而 PostgreSQL 遇到不存在的配置参数会直接报 unrecognized configuration parameter，让整个请求 500。

END IF 里——有 pgvector 时一行都不执行，不与原生运算符冲突。建库脚本用 psql 的 \if :use_native / \else / \endif 切换 DDL（PostgreSQL 10+ 支持条件元命令）。

（三）关键设计：AI 为什么改不了权属（四层防护）

需求原文是"明确 AI 只写建议，绝不直接改 asset.right_level"。这个要求如果只靠"我记得别写"，三个月后必然被某次紧急需求打破。所以用四层机制焊死：

1. 第一层：数据库列级权限（最硬）

ich_heritor 的 UPDATE 权限清单里没有 right_level。即便应用代码写出 UPDATE asset SET right_level=...，数据库会抛 InsufficientPrivilege，被 main.py 的异常处理器转成 403 + "数据库层权限拒绝"。这不是应用层的 if role == 'expert'，而是数据库自己拒绝。绕过应用层也绕不过它。

2. 第二层：源码不变量测试

tests/test_invariants.py 直接扫描源码字符串：analyze_asset 函数体里不得出现写 right_level 的 SQL；全工程只有 approve_asset 一处出现 SET right_level；classifier.py 不得 import app.db / app.services。共 64 项检查。任何人日后想加一条"AI 自动确权"的捷径，测试立刻红。

3. 第三层：分级器物理隔离

classifier.py 是纯函数模块，没有数据库连接对象，物理上写不了数据（详见第三章第二节第 3 点）。

4. 第四层：写入路径唯一 + 事务留痕

就算前三层都被绕过，right_level 的每次变更都会被 trg_asset_right_change 写入 system_audit_log（含新旧快照与 changed_fields）。而 system_audit_log 自己有 trg_syslog_immutable 防篡改触发器 + REVOKE UPDATE, DELETE。谁改的、何时改的、从什么改成什么、用什么数据库角色改的——全部留痕，且改不掉。

四层的关系是"纵深防御"：第一层挡应用层越权，第二三层挡开发期引入的回归，第四层是最后的事实记录。任何单层失效都不至于让系统失去约束力。

（五）阈值与权重如何确定

分级阈值 0.92 / 0.80：这是经验值，来自 builtin 特征在样例纹样上的实测分布——同一纹样不同扫描件相似度通常 >0.90，不同纹样在 0.6~0.8 区间。0.92 略高于"同纹样下限"，留出安全边际；0.80 取不同纹样的上界。

必须说明这是经验值，不是统计标定的结果。项目文档给出了正式标定方法：在真实非遗图像数据集上画 ROC／PR 曲线找最佳切点。当前阈值让系统可用，但不构成学术意义上的"最优阈值"。

特征段权重 0.51 / 0.23 / 0.26：由 tests/tune_weights.py 网格搜索得到，目标函数为双约束（翻拍稳定性 ≥0.90 且改编相似度 <0.92）。标定脚本保留在仓库，features.py 里写明了"若当前取值无法同时满足两个约束，脚本会以非零码退出并告警"。

八、结论

本选题从一个具体的现实问题出发——非遗数字资产在数字化过程中出现的"公有母题被私有化圈占、改编幅度无法量化、权属结论不可追溯"，把它转化为一个可用技术手段部分解决的分级确权问题：用图像向量相似度作为借鉴程度的客观代理指标，用 PostgreSQL 的约束、触发器、视图、事务与权限体系保证判断过程的规范性。

项目的技术重点不在算法创新，而在工程约束的落实。需求中"AI 只写建议、绝不直接改权属"这一条，如果只写进文档就形同虚设；本项目用四层机制（数据库列级 GRANT、源码不变量测试、模块依赖隔离、触发器留痕）把它变成"物理上做不到"，并且用 192 项测试持续守护这个不变量。

项目目前已交付一个可运行、可演示、有完整测试证据的系统，同时如实声明了最大的一处验证缺口——SQL 脚本未在真实 PostgreSQL 上执行。这一声明不是免责，而是把风险显式化：列出 4 个可能出问题的位置、给出对应的修复方案、提供逐层诊断工具。第四章与第七章中记录的 4 个主动发现并修复的缺陷，也说明"逐行审查 + 负向回归"这套替代验证手段确实有效。

作为数据库原理课程设计，本项目覆盖了课程要求的核心要素：3NF 与垂直拆分、7 类索引（普通／部分／部分唯一／组合／HNSW／GIN）、7 个触发器（审计／维护／防篡改／守卫／归一化）、3 个视图（含 LATERAL 与 UNION ALL）、悲观锁与事务原子性、列级 GRANT 与最小权限原则。这些不是"为了覆盖考点而加"，每一条都对应一个真实业务约束的落地需求。
